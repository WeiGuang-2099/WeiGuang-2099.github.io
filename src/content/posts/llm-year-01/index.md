全书分三层：**战术（Tactical）→ 运营（Operational）→ 战略（Strategic）**。第 1 章是最底层也是最“上手”的一层，回答的问题是：**拿到一个 LLM 之后，具体怎么做才能把 Demo 变成可靠的产品？**

作者给出的答案是四块积木，而且是有先后顺序的：

| 顺序 | 积木 | 一句话主旨 | 核心动作 |
|---|---|---|---|
| ① | **Prompting（提示）** | 先从 Prompt 起步，别一上来就微调 | 三大基本功 + 结构化输入输出 + 拆小 Prompt + 精雕上下文 |
| ② | **Retrieval / RAG（检索）** | 用检索给模型“喂知识”，而不是改模型 | 看相关性/密度/细节三指标，关键词做基线，混合检索 |
| ③ | **Workflow Tuning（工作流）** | 超越单次 Prompt，把任务拆成多步流程 | 多步 Flow、确定性优先、多样性、缓存、何时微调 |
| ④ | **Evaluation & Monitoring（评估）** | 没有评估，上面三块都无法迭代 | 断言式单测、LLM-as-Judge、实习生测试、防 Goodhart 定律 |

一个贯穿全章的思维方式是：**LLM 应用 = 一个概率组件 + 一圈确定性的工程外壳。** 模型本身是随机、不可靠、会撒谎的；所有技巧（结构化输出、确定性工作流、缓存、护栏、评测）本质上都是在用确定性手段把这个概率组件“框住”。抓住这条主线，本章所有小节都能串起来。

## Prompting（提示）

### 先从 Prompt 开始：既别低估，也别高估

**【原文】** 开发新应用时建议从 Prompting 开始。它容易被**低估**——用对了技巧能走很远；也容易被**高估**——即使 Prompt 很棒，要让它在真实环境稳定工作，仍需在 Prompt 周围做大量工程。

**【扩展】** 这句话背后的经济学：Prompt 迭代的成本近乎为零（改几行字、跑一次评测），而微调、自托管、换模型每一项都是数量级更高的投入。所以正确的做法是沿“成本阶梯”爬：

```
改 Prompt → 加示例(n-shot) → 加结构化约束 → 拆成多步流程 → 加检索(RAG) → 缓存 → 最后才是微调
低成本 ────────────────────────────────────────────────────▶ 高成本
```

每上一层，都要先问：“上一层真的到顶了吗？”

### 三大基本功：n-shot、思维链、提供相关资源

#### n-shot 提示 + 上下文学习（In-Context Learning）

**【原文】** 给模型几个示例来演示任务、对齐输出格式。四条经验：

1. **n 别太少**：示例太少模型会过度“锚定”在那几个例子上，泛化变差。经验值 **n ≥ 5**，多到几十个也没问题。
2. **示例要代表真实输入分布**：做电影摘要器，就按实际比例放入不同类型的电影。
3. **不必给完整的“输入—输出”对**：很多时候只给“期望的输出长什么样”就够了。
4. **如果模型支持工具调用，示例里也要展示工具的用法**。

**【扩展】为什么 n 太少会“过度锚定”？** 示例在模型眼里不只是“任务说明”，它同时传递了：标签分布、格式、语气、长度、甚至答案倾向。示例少意味着每个示例的“权重”很大，模型会把偶然特征当成规律。相关的学术发现（书未提及）：

- **多数标签偏差 / 近因偏差**：Zhao 等人发现，如果示例里答案大多是某个标签，或者最后一个示例是某标签，模型会明显偏向该标签（[Zhao et al., 2021](https://arxiv.org/abs/2102.09690)）。→ 启示：**示例的标签要均衡，顺序要打乱**。
- **顺序敏感**：Lu 等人发现仅改变示例的排列顺序，同一模型在同一任务上的准确率可以在接近随机到 SOTA 之间波动（[Lu et al., 2021](https://arxiv.org/abs/2104.08786)）。→ 启示：**把示例顺序也当作需要评测的超参数**。

**补充例子（客服工单分类）**：假设有“退款/物流/质量/其他”四类，n=4 且每类一个示例。问题是“其他”这个兜底类极难从 1 个示例学会，模型会把模糊工单硬塞进前面三类。改为 n=12，每类 3 个，且“其他”里刻意放入几条“看起来像退款但其实不是”的难例，泛化明显改善。这正是“示例要代表真实分布 + 覆盖边界”的含义。

#### 思维链（Chain-of-Thought, CoT）

**【原文】** 让模型在给最终答案前先解释推理过程，相当于给它一块“草稿纸”，不必全靠“记忆”完成。最早的零样本做法是加一句“Let's think step by step”，但作者发现**把 CoT 写具体**往往更有效——多加一两句明确步骤的指令，就能显著降低幻觉。

例子（会议纪要摘要）：① 先在草稿区列出关键决策、待办事项及负责人；② 核对草稿区内容与原文是否事实一致；③ 最后综合成简洁摘要。

作者也坦诚：近期有研究质疑 CoT 是否有传说的那么强（书里链的是 [Stechly 等人 2024 年的 *Chain of Thoughtlessness?*](https://arxiv.org/abs/2405.04776)），而且推理时到底发生了什么也有争议——但这仍是值得实验的技术。

**【扩展】这里值得展开，因为它是全书出版后变化最大的地方之一。**

| 时间 | 认识 | 对本章的影响 |
|---|---|---|
| 2022 | Wei 等人提出 few-shot CoT（[Wei et al., 2022](https://arxiv.org/abs/2201.11903)）；Kojima 等人提出零样本 CoT（[Kojima et al., 2022](https://arxiv.org/abs/2205.11916)） | 本章技巧的来源 |
| 2023 | **Self-Consistency**：对同一问题采样多条推理链再投票，比单条 CoT 更稳（[Wang et al., 2022](https://arxiv.org/abs/2203.11171)） | 本章未提，实用性强 |
| 2023 | **CoT 不忠实**：模型写出来的理由未必是它得出答案的真实原因，CoT 可能是“事后合理化”（[Turpin et al., 2023](https://arxiv.org/abs/2305.04388)） | 书里说推理时发生了什么“有争议”，没给出处；CoT 不忠实是这类争论之一 |
| 2024.9 之后 | **推理模型**（OpenAI o1、DeepSeek-R1 等）把“先思考再答”训练进了模型本身，模型自主决定思考多久 | 手写 CoT 的边际价值下降，但“把步骤写具体”仍适用于非推理模型与流程设计 |

**实践结论（我的判断）**：
- 用普通指令模型时，**具体化的 CoT 仍是最划算的技巧**，尤其是有明确步骤可拆的任务（抽取→核对→综合）。
- 用推理模型时，手把手写“第一步…第二步…”不再是默认动作：有研究发现它在一部分任务上会拉低表现（[Liu et al., 2024](https://arxiv.org/abs/2410.21333)），在其他任务上效果不一。先把**目标和验收标准**说清楚，要不要再加步骤，按任务用评测验证。
- CoT 的最大工程价值不在“想得更对”，而在**把中间产物暴露出来**——可观测、可断言、可单独评测。这一点与 1.4“拆小 Prompt”完全一致。

**补充例子（Text-to-SQL 的 CoT）**：朴素提示直接要 SQL。具体化 CoT 则要求：先列出问题涉及的表与列并说明理由；再写出需要的 JOIN 关系；再写 SQL；最后自查一遍“每个 SELECT 的列是否都有明确来源”。中间产物（涉及的表列）恰好能用来做断言测试。

#### 提供相关资源（Providing Relevant Resources）

**【原文】** 把文本片段直接给模型用，可以扩充知识、减少幻觉、增加用户信任，通常通过 RAG 实现。关键是：**光把资料塞进去不够**，还要明确告诉模型——优先使用这些资料、直接引用、并在资料不足时明说。

**【扩展】这是 RAG 里最常见的“差一句话”问题。** 很多 RAG 效果差不是检索差，而是指令缺了三条：

```text
1. 只依据 <资料> 回答，不要使用你自己的知识。          ← 限定知识来源
2. 回答时注明依据的是哪条资料（编号）。                  ← 强制引用
3. 如果 <资料> 不足以回答，明确说"资料中没有相关信息"。   ← 允许"不知道"
```

第 3 条直接对应 4.7 节“LLM 不该输出时也输出”——不给“不知道”的出口，模型就会编。

### 结构化你的输入和输出

**【原文】**
- **结构化输入**：给输入加序列化格式，能提供更多线索——token 之间的关系、附加元信息（类型）、并让请求更接近训练数据里的样子。典型例子：网上讲 SQL 的问题都会先给 Schema，所以 Text-to-SQL 的有效提示也应该包含结构化的 Schema 定义。
- **结构化输出**：目的类似，另外还能简化与下游系统的集成。工具建议：调用 API SDK 用 **Instructor**，自托管 Hugging Face 模型用 **Outlines**。
- **模型家族有偏好**：Claude 偏好 XML，GPT 偏好 Markdown 和 JSON。用 XML 还可以**预填回复**——在 assistant 消息里给出 `<response><name>`，模型就从这里接着写。

**【扩展】**

1. **为什么“像训练数据”很重要？** LLM 本质是在续写。输入格式越接近它训练时见过的格式，它越容易进入正确的“模式”。Schema + 样例值 + 自然语言问题三件套，几乎是所有 SQL 教科书的写法，模型对这种模式非常熟。

2. **预填回复的本质是约束解码的“穷人版”**。更彻底的做法是**受限解码（constrained decoding）**：直接在采样阶段屏蔽不合法的 token，保证输出 100% 符合 JSON Schema 或正则/语法。Outlines、vLLM 的 guided decoding 都是这条路；主流 API 厂商在 2024 年下半年也陆续推出了保证 Schema 的结构化输出接口。书出版时这还是“技巧”，现在已是基础设施。

3. **我自己的预填示例（抽取任务）**：

```python
messages = [
    {"role": "user", "content": (
        "从 <邮件> 中提取信息，填入 <回复> 标签。\n"
        "<邮件>你好，我上周三订的那台黑色加湿器还没到，订单号 A1024，能帮我查下吗？——李女士</邮件>\n"
        "<回复>使用 <商品>、<颜色>、<订单号>、<诉求> 标签。缺失信息填 未知。</回复>"
    )},
    {"role": "assistant", "content": "<回复><商品>"}   # 预填：强制从这里开始
]
```

4. **一个安全提醒**：XML/JSON 标签让结构更清晰，但也意味着**用户输入可以被伪装成结构**（提示注入）。实践上应把用户数据放在明确的边界标签内，并在系统提示中声明“标签内是数据而非指令”，同时对输出做校验。

### 小而专的 Prompt：一个 Prompt 只做一件事

**【原文】** 软件里有“上帝对象（God Object）”反模式——一个类/函数干所有事。Prompt 也一样。Prompt 从几句话起步，为了处理边界情况不断加指令、加推理步骤、加示例，最后变成 **2000 token 的“科学怪人”**——而且在最常见、最简单的输入上表现反而更差了。GoDaddy 把这一点列为他们构建 LLM 应用的头号教训。

解法：像重构代码一样重构 Prompt。会议纪要摘要器可拆成三步：① 抽取决策/待办/负责人为结构化格式；② 对照原文核对一致性；③ 基于结构化内容生成摘要。好处是每个 Prompt 都能**单独迭代和评测**。

**【扩展】**

- 这和软件工程的“单一职责原则”是同构的，更深的原因在于 LLM 的**指令遵循能力随指令数量递减**：指令越多，单条被忽略的概率越大；边界情况的处理逻辑又会干扰主路径。
- 这也是后面所有内容的地基：拆出来的每一步，才能配上断言测试（4.1），才能做成确定性工作流（3.2），才能缓存中间结果（3.4）。**“拆小”是全章的枢纽动作。**
- 成书后 Anthropic 发布的 *Building Effective Agents* 把“提示链（prompt chaining）”列为最基础的工作流模式，与本章结论互相印证。
- **经验法则（我的总结）**：当一个 Prompt 同时出现 ① 超过 3 个可清晰分开的子目标，② “先…然后…最后…”超过 3 步，③ 针对不同情况的 if-else 超过 3 条 ——就该拆了。

**补充例子（简历筛选）**：上帝 Prompt：“读简历和 JD，打分，写优缺点，给出面试建议，如果不足 3 年经验则……如果是技术岗则……”。拆后：① 从简历抽取结构化信息（年份、技能、项目）；② 从 JD 抽取硬性要求与加分项；③ 逐条比对输出表格；④ 基于表格生成结论。每一步都可单独测，第 ③ 步的输出还能直接给 HR 看做解释。

### 精雕你的上下文（Craft Your Context Tokens）

**【原文】** 重新审视你到底需要给模型发多少上下文。像米开朗基罗那样——不是往上堆，而是**把多余的部分凿掉**。RAG 负责把所有“可能相关的大理石块”搬过来，但你做了什么来提取必要部分？

一个极实用的方法：把最终发给模型的完整 Prompt（含所有拼接、元提示、RAG 结果）**放到空白页上，当成一篇文章读一遍**。作者用这个方法发现了冗余、自相矛盾的措辞和糟糕的格式。

另一个关键是上下文的**结构**：一袋子文档（bag-of-docs）对人没帮助，别假设对 Agent 就有。要仔细设计结构，凸显各部分之间的关系，让“提取”尽可能简单。

**【扩展】**

1. **“读一遍最终 Prompt”是本章性价比最高的建议**，但极少有团队真的做。RAG 应用的最终 Prompt 往往是系统提示 + 历史对话 + 10 个 chunk + 用户问题拼起来的一团东西，而且因为路径众多，从没人完整看过它。建议把它做成开发流程的固定环节：每次上线前随机抽 20 条真实请求，把完整 Prompt 导出来人工读。

2. **“Lost in the Middle”**：Liu 等人发现模型对长上下文的开头和结尾利用得好，**中间部分的信息利用率明显下降**（[Liu et al., 2023](https://arxiv.org/abs/2307.03172)）。这直接支持“结构很重要”：把最重要的约束和资料放在开头和结尾，并在 chunk 前加简短的标题/来源/日期元信息，而不是裸文本拼接。

3. **成书后的新证据**：Chroma 团队 2025 年的“Context Rot”研究指出，即使任务完全在窗口容量内，随着输入变长，模型在简单任务上的表现也会系统性下滑。这为“凿掉多余内容”提供了比 2024 年更坚实的论据：**多余的上下文不是免费的，它会主动伤害表现**。

4. **结构化 chunk 的示例（我的写法）**：

```text
[资料 3 | 来源: 产品手册 v2 | 更新: 2024-05]
标题: 退货政策
正文: 未拆封商品可在收货后 30 天内退货……

[资料 7 | 来源: 在线客服记录 | 更新: 2024-06]
标题: 退货咨询
正文: 客户询问已拆封商品能否退货，客服答复……
```

对照：“未拆封商品可在收货后 30 天内退货……客户询问已拆封商品能否退货……”——后者把两条相互矛盾的来源揉在一起，模型很难正确取舍。

## 信息检索 / RAG

### RAG 的好坏取决于三个维度：相关性、信息密度、细节程度

**【原文】** RAG 让模型基于提供的上下文做上下文学习，比微调省力省钱得多。但 **RAG 的上限就是检索到的文档的质量**。

| 维度 | 含义 | 书中度量/例子 |
|---|---|---|
| **相关性 Relevance** | 检回的东西对不对题 | 用 **MRR**、**NDCG** 等排序指标；用“打乱检索结果”实验测排序对下游的影响 |
| **信息密度 Density** | 同等相关时，更简洁、废话更少的那篇更好 | 电影评论：高赞评论和编辑评论比全量评论密度更高 |
| **细节程度 Detail** | 给的信息够不够模型理解语义 | Text-to-SQL：只给列名 → 再给列描述 → 再给代表性取值，SQL 正确率逐步提高 |

**【扩展】**

**① MRR / NDCG 到底在量什么？**

- **MRR**（Mean Reciprocal Rank）：对每个查询，取“第一个相关结果所在排名的倒数”，再对所有查询取平均。

  例：3 个查询，第一个相关结果分别在第 1、2、4 位 → MRR = (1/1 + 1/2 + 1/4) / 3 ≈ **0.58**。含义是“用户平均要多翻几个结果才碰到相关的”。
- **NDCG**（Normalized Discounted Cumulative Gain）：考虑所有结果的相关性等级，并按位置打折（排得越靠后，贡献越小），再除以理想排序的得分做归一化，范围 0～1。来源是 Järvelin 与 Kekäläinen 在 2002 年的工作。

- **什么时候用哪个**：只需一个正确答案（FAQ、精确事实查询）→ MRR；需要多条都有用且顺序重要（摘要、综合分析）→ NDCG。

**② “打乱实验”是很聪明的因果检验**：用同样的文档、只打乱顺序再跑一遍下游任务。如果结果明显变差 → 排序很关键，值得投资重排（rerank）；如果几乎没变 → 要么模型自己能挑，要么你的检索结果其实没在起作用——**后者是个警报**。

**③ 增加细节的代价与边界**：细节越多，上下文越长、成本越高，而且“Context Rot”意味着噪声也会增加。我的经验顺序：先加列/字段描述（便宜且几乎总是有效），再加少量样例值（对枚举类、编码类字段尤其有效），最后才考虑加完整文档。

**补充例子（低代码平台公式助手）**：用户问“怎么算逾期天数”。只给函数名列表，模型会编不存在的函数 `DATEDIFF`；给上每个函数的签名、一句话说明、一个例子，再加上平台里 3 个真实公式的样例，正确率显著提高。这正是“细节程度”的直接体现。

### 别忘了关键词检索：做基线，也做混合检索

**【原文】** 嵌入式 RAG 的 Demo 太流行，以至于人们忘了信息检索领域几十年的积累。嵌入向量能捕捉高层语义相似度，但在**具体的关键词型查询**上会失灵——人名（如 Ilya）、缩写（如 RAG）、ID（如 claude-3-sonnet）。而 **BM25** 这类关键词检索正是为此而生。用户已经习惯了关键词检索的行为，期望的文档检索不到会很恼火。Perplexity 的 CEO 和 Sourcegraph 的 CTO 都持类似观点：向量并不能神奇地解决搜索，在 BM25 之上做出真正的改进很难。

关键词检索的另外两个优点：**可解释**（能看到命中了哪些词）；**计算高效**（Lucene、OpenSearch 优化了几十年）。

多数情况下**混合检索最好**：关键词负责精确匹配，嵌入负责同义词、上下位词、拼写错误，以及多模态。Shortwave 分享过他们的 RAG 流水线：查询改写 → 关键词 + 嵌入检索 → 排序。

**【扩展】**

1. **为什么嵌入会败给人名和 ID？** 嵌入把 token 压缩成一个稠密向量，目标是“语义相近”；罕见专有名词和 ID 在训练数据里很少见，其向量不够有区分度，而 `claude-3-sonnet` 和 `gpt-4-turbo` 在语义空间里可能离得很近（都是“模型名”）。BM25 则是精确的词项匹配，罕见词的 IDF 权重反而很高——**恰好擅长嵌入最弱的地方，所以互补**。

2. **BM25 简要回顾**（Robertson & Zaragoza, 2009）：对一个查询，每篇文档的得分是各查询词得分的加和；每个词的得分取决于 ①词在文档里的频率（饱和增长，参数 k₁）、②词的稀有程度（IDF）、③文档长度的归一化（参数 b）。不需要训练，调两个参数就能上线。

3. **混合检索怎么融合？** 最常用的是 **RRF（Reciprocal Rank Fusion）**：对每篇文档，把它在各路检索里的排名取倒数后相加（Cormack et al., 2009）。不需要分数归一化，简单且稳健。进阶做法：粗召回之后加一个 **cross-encoder 重排器**对前 50 条精排——这是“重排”一词在书中的含义，也是目前 RAG 的标配。

4. **中文场景的特别提醒（书中没有）**：中文没有空格，BM25 需要先分词（如 jieba）或用二元分词；专有名词、品牌名、型号常被切错。实践上可以用“分词 BM25 + 字面 n-gram”多路召回来兜底。此外，中文嵌入模型的选择（是否针对中文语料训练、是否支持 instruction 前缀）对召回影响很大，务必用自己的数据做评测，不要只看榜单。

5. **查询改写**：书中 Shortwave 的案例提到“查询改写”。常见手法有：指代消解（把“它”换成具体的物）、多查询扩展（一个查询改写成 3 个角度）、**HyDE**——先让模型写一段假想答案，再用这段答案去做嵌入检索（[Gao et al., 2022](https://arxiv.org/abs/2212.10496)），因为“答案与答案”的嵌入往往比“问题与答案”更接近。

**补充例子（企业 IT 知识库）**：用户问“错误码 ERR-4021 怎么解决”。纯向量检索可能返回一堆“错误码处理指南”的泛泛文章；BM25 一击命中含 “ERR-4021” 的那篇。反过来问“电脑开不了机”，BM25 找不到“无法加电”的那篇，向量能找到。混合检索两头都赢。

### 注入新知识：优先 RAG，而非微调

**【原文】** 两者都能给 LLM 加新知识、提升特定任务表现，先试哪个？近来的研究显示 RAG 占优：一项研究把 RAG 与无监督微调（继续预训练）对比，在 MMLU 子集和时事问题上，RAG 无论对训练中见过的知识还是全新知识都更稳定地胜出；另一篇在农业数据集上对比 RAG 与监督微调，RAG 的提升同样更大，在 GPT-4 上尤其明显。

除效果外，RAG 的工程优势：
1. **更新便宜**：维护检索索引远比继续预训练/微调便宜。
2. **可删除**：索引里有有害内容，直接删改文档即可；微调后则很难“忘掉”。
3. **权限可控**：分区索引能保证每个租户只能检索自己的文档，不会泄露给别的组织。

**【扩展】**

- **为什么微调不擅长加知识？** 知识被“写进”参数后，是分布式、不可编辑、不可追溯的，而且模型容易把“学过相关内容”和“真的知道这件事”混淆——反而更容易一本正经地编。而 RAG 把知识外置，答案能带着出处返回，这与 1.2.3 的“强制引用”配合得很好。
- **口诀**：**知识用 RAG，行为用微调。** 需要模型“知道新事实”→ RAG；需要模型“以特定方式说话/输出特定 DSL”→ 微调（见 3.5）。
- **两者并不互斥**：常见组合是“微调一个小模型专门做查询改写/重排/摘要，RAG 负责提供事实”。
- **一个常被忽视的风险**：RAG 的质量取决于文档质量。文档过时、相互矛盾、权限错误，都会**原样传给用户**。所以 RAG 的运营本质上是一个**文档治理问题**——这比换一个嵌入模型重要得多。

### 长上下文不会让 RAG 过时

**【原文】** Gemini 1.5 提供了最高 1000 万 token 的上下文窗口，有人因此宣称“大窗口杀死了 RAG”——把所有数据丢进去直接聊就行。作者认为 RAG 被夸大的死亡消息由来已久，理由有三：

1. **仍然需要“选择”**：窗口再大，也总放不下所有数据，仍然需要决定放什么。
2. **推理能力未被证实**：除了“大海捞针”这类窄测试，还没有令人信服的数据表明模型能在这么大的上下文上有效推理；没有好的检索和排序，就会用干扰项淹没模型，甚至塞满完全不相关的内容。
3. **成本**：Transformer 的推理开销随上下文长度平方增长（或在时间/空间上各线性）。有模型能在回答每个问题前读完你公司的整个 Google Drive，不代表这是好主意。**类比内存与磁盘**：即使有几十 TB 内存的机器，我们依然读写磁盘。

结论：RAG 这个模式在窗口变大的情况下依然有用。

**【扩展】成书两年多后回看，这一节是本章“最经得起时间考验”的部分。**

| 书中预言 | 2025–2026 年的证据 |
|---|---|
| “大海捞针不等于长文推理” | **NoLiMa**（2025）显示，一旦把“字面重合”捷径去掉、要求语义关联，多数模型在 32K 就把短文本基线丢了一半左右；**RULER**（[Hsieh et al., 2024](https://arxiv.org/abs/2404.06654)）显示标称 1M 窗口的模型，有效长度可能远小于标称值 |
| “模型会被干扰项淹没” | “Context Rot”研究显示性能随输入长度非均匀退化 |
| “成本是问题” | 全量塞入 vs. 精准检索 1 万 token，单次成本与首 token 延迟差距很大（各博客给出的倍数不一，但量级结论一致） |

今天的工程共识已经收敛为：**不是二选一，而是按场景路由，且两者组合。**

| 场景 | 首选 | 理由 |
|---|---|---|
| 单篇长文档精读、合同/代码评审 | 长上下文直塞 | 需要“全局视野”，切块会破坏跨条款关系 |
| 小而稳定的语料（产品 FAQ） | 长上下文 + Prompt 缓存 | 免索引、免维护 |
| 万级文档的企业知识库 | RAG | 装不下；需要权限、审计、引用溯源 |
| 时效性强的数据 | RAG / 工具调用 | 增量更新索引，不必重读全文 |
| 多跳关系、全局归纳 | GraphRAG / Agentic RAG | 纯向量切块会切断文档间的隐含关系 |

而最流行的组合模式正是书中的内存/磁盘类比：**先 RAG 从海量文档里缩到 Top-N，再把这 N 篇整篇放进长窗口做跨文档推理**——“检索做找，窗口做读”。

一个书中没有强调、但现在很关键的点：**长上下文会吃掉你的缓存**。如果每次请求都带 50 万 token 的资料，即使有前缀缓存，价格与延迟也远高于 1 万 token 的精准检索；而且一旦资料更新，缓存前缀就会失效。

## 调优与优化工作流（Tuning and Optimizing Workflows）

### 多步“流程”能带来巨大提升

**【原文】** 把一个大 Prompt 拆成多个小 Prompt 能得到更好的结果。典型例子是 **AlphaCodium**（代码竞赛）：从单条 Prompt 切换到多步工作流后，GPT-4 在 CodeContests 上的 pass@5 从 **19% 提升到 44%**。流程包括：① 反思问题；② 推理公开测试；③ 生成多个候选方案；④ 对方案排序；⑤ 生成合成测试；⑥ 在公开测试与合成测试上迭代。

**小任务 + 清晰目标 = 最好的 Agent/Flow Prompt。** 不是每一步都要结构化输出，但结构化输出能极大地方便与编排系统对接。

作者给出可尝试的做法：
- 显式的规划步骤，规格尽量明确；
- 预定义若干计划供选择；
- 把用户原始 Prompt 改写成 Agent Prompt——**注意这一步是有损的**；
- 用线性链、DAG、状态机来组织 Agent 行为，不同规模适合不同结构；
- **规划校验**：规划里包含“如何评估其他 Agent 的回答”的指令，确保最终组装得当；
- **固定上游状态做 Prompt 工程**：Agent 的 Prompt 要针对上游可能出现的多种变体分别评测。

**【扩展】**

- AlphaCodium 来自 Ridnik 等人 2024 年的工作（[Ridnik et al., 2024](https://arxiv.org/abs/2401.08500)）。它的流程本质上是把软件工程师的做题过程显式化：理解 → 用测试倒推 → 多方案 → 筛选 → 自造测试 → 迭代。
- **为什么多步会更好？** 三个原因：① 每一步的 Prompt 更短、指令更聚焦（回到 1.4）；② 中间产物可以被检查、被驳回、被重做（自我修正）；③ 多候选 + 排序引入了“搜索”而不是“一次生成”。
- **“改写用户 Prompt 是有损的”** 这句话很重要。改写者（无论是模型还是人）会丢掉用户意图里的细节，也会加入自己的理解。建议：改写后保留原始请求，一并传给下游；并在评测里专门测“改写后的意图保真度”。
- **相关学术脉络**：Plan-and-Solve（[Wang et al., 2023](https://arxiv.org/abs/2305.04091)）就是“先写计划，再执行”的早期代表；Tree-of-Thoughts 则在“多候选 + 评估 + 回溯”上更进一步。它们都与 AlphaCodium 的思路同源。

**补充例子（调研报告生成）**：单 Prompt：“写一份关于 X 市场的调研报告”。多步流程：① 把问题拆成 5～7 个子问题；② 每个子问题检索 + 回答；③ 检查每个子答案是否有引用支撑；④ 找出子答案之间的矛盾并解决；⑤ 生成大纲；⑥ 按大纲写报告；⑦ 对照子答案核查每段事实。第 ③⑦ 步就是“规划校验”。

### 目前优先选择确定性工作流

**【原文】** Agent 能动态响应用户与环境，但其非确定性让部署变得困难。**每一步都有失败的可能，而错误恢复的能力很差，所以多步任务的成功率随步数增加呈指数下降。** 因此做 Agent 的团队很难部署出可靠的 Agent。

一个有前景的做法：让 Agent **生成确定性的计划**，再以结构化、可复现的方式执行。第一步给定高层目标生成计划，然后确定性执行。好处：
1. 生成的计划可以作为 few-shot 样本，或用于微调 Agent；
2. 确定性执行让系统更可靠，更易测试和调试，失败能追踪到计划中的具体步骤；
3. 计划可表示为 **DAG**，相比静态 Prompt 更易理解、更易适配新情况。

作者还有一句妙语：**最成功的 Agent 构建者可能是那些带过初级工程师的人**——因为生成计划的过程就像指导新人：我们给新人清晰的目标和具体的计划，而不是模糊的开放式指令，对 Agent 也该如此。

结论：可靠的 Agent 的关键在于更结构化、更确定性的方法，以及收集数据来优化 Prompt 和微调模型；否则做出来的 Agent 会“偶尔表现得极好，但平均而言让用户失望”，导致留存很差。

**【扩展】**

**① 把“指数下降”算出来更有体感。** 设每一步成功率 p，n 步全对的概率为 pⁿ：

| 单步成功率 | 5 步 | 10 步 | 20 步 |
|---|---|---|---|
| 95% | 77% | 60% | 36% |
| 90% | 59% | 35% | 12% |
| 80% | 33% | 11% | 1% |

如果产品要求端到端成功率 ≥ 90%，单步 95% 时最多只能承受约 2 步。这个表是本章所有“保守”建议的数学根源。

**② 为什么确定性工作流有效？** 它把 pⁿ 里的一部分 n 从“模型步骤”换成了“代码步骤”（代码的成功率≈100%）。例如 10 步里有 6 步改为代码，模型只剩 4 步，0.95⁴ ≈ 81% 而非 60%。

**③ “计划 → 执行”的额外好处**：计划本身是可读的，可以**让用户审批后再执行**（人在回路），这对高风险操作（发邮件、转账、删数据）几乎是必需的。

**④ 成书之后的变化（需要修正的部分）**：2024 年下半年到 2025 年，推理模型与工具使用能力大幅提升，端到端自主 Agent（自主写代码、自主操作电脑）的能力比成书时强很多；MCP（2024 年 11 月发布）等协议也让工具接入标准化了。因此“目前优先确定性”里的“目前”在松动。但**我的判断是核心原则没变，只是适用边界扩大了**：
- 探索型、低风险、有验证器的任务（写代码跑测试、搜索调研）→ 自主 Agent 已可实用；
- 高风险、不可逆、强合规的任务 → 仍是确定性工作流 + 审批。
- 而且自主 Agent 的“自我纠错”能力恰恰依赖**外部验证器**（编译器、测试、检索结果），这与 AlphaCodium“生成合成测试再迭代”是同一思路——**验证器才是可靠性的来源，而不是更聪明的模型本身**。

**⑤ 实践上的中间形态**：把 Agent 限定在“有限状态机”里——状态集合固定、转移条件由代码判断、模型只在每个状态内做“填空”。这比全开放的 ReAct 循环可控得多，也比纯线性流程灵活。

### 超越 Temperature：获得更多样的输出

**【原文】** 假设你在做商品推荐：根据用户买过的商品推荐新商品。多次运行发现结果太相似，于是调高 temperature。temperature 让下一个 token 的概率分布变得更平，通常不太可能的 token 更容易被选中。但调高 temperature 会带来一些失败模式：

- 目录里本来很合适的某些商品**永远不会出现**；
- 训练数据里与 Prompt 高度相关的少数几个商品**被过度代表**；
- temperature 太高会出现**不存在的商品**（或胡言乱语）。

也就是说，提高 temperature 并不能保证模型从你期望的分布（比如均匀随机）中采样。作者给出其他增加多样性的方法：

1. **调整 Prompt 里的元素**：例如 Prompt 模板里有历史购买列表，每次插入时**打乱顺序**，影响就很显著。
2. **维护最近输出列表**：明确要求不要推荐列表里的商品，或者对与近期推荐相似的输出拒绝并重采样。
3. **变换提问角度**：比如“挑一个用户会经常用的商品”、“选一个用户会推荐给朋友的商品”，转移关注点从而影响多样性。

**【扩展】**

- **为什么 temperature 不够？** temperature 只是重新分配**模型已有分布**的概率质量。如果模型对“某几个商品”赋予了绝大部分概率，调高 temperature 首先是在“尾巴”里引入噪声，而不是把概率质量均匀搬到其他好商品上。**分布的形状问题，靠温度解决不了。** 另外长输出的质量会随 temperature 升高迅速崩坏，因为每一步都在“裸奔”。
- **其他采样参数**：top-p（核采样）限制候选集合；**min-p**（2024 年提出）按最高概率的比例动态截断，据报告在高 temperature 下比 top-p 更稳。但这些都仍在“模型已有分布”内操作。
- **多样性其实有三个层次**，对应不同的解法：

| 层次 | 问题 | 解法 |
|---|---|---|
| 采样层 | 同一 Prompt 输出雷同 | temperature / top-p / min-p |
| 提示层 | 模式单一 | 书中的打乱顺序、换角度、排除列表 |
| 系统层 | 缺少多样性约束 | 在检索阶段做 MMR（最大边际相关性）、聚类后每类取一个；用嵌入做去重 |

- **去重/排除列表的工程细节**：字符串匹配不够，“真皮沙发”与“皮质三人沙发”语义重复。实践上用嵌入余弦相似度（阈值约 0.85～0.9，需按数据调）做“最近输出”的语义去重，比精确匹配有效得多。
- **多样性 vs. 相关性的权衡**：多样性应以“**相关性约束下的多样性**”为目标——先保证每个候选都相关，再在其中求不同。书中“用不同提问角度”正是在相关的前提下移动分布。

### 缓存被低估了

**【原文】** 缓存通过避免对相同输入重新生成来节省成本、消除生成延迟。并且，如果一条回复此前已通过护栏检查，就可以直接提供这些经过审查的回复，降低提供有害或不恰当内容的风险。

- 最直接的做法：给被处理的条目使用**唯一 ID**（如文章、商品评论）。请求到来时先查缓存里有没有摘要，有就立即返回，没有就生成 → 过护栏 → 返回 → 存入缓存。
- 对于开放式查询，可以借鉴搜索领域的做法，同样利用缓存。**自动补全和拼写纠正**等功能还能帮助规范化用户输入，从而提高缓存命中率。

**【扩展】LLM 应用里其实有四种“缓存”，别混为一谈：**

| 类型 | 缓存的是什么 | 命中条件 | 典型工具/机制 |
|---|---|---|---|
| **精确缓存** | 完整响应 | 输入完全一致（ID 或哈希） | Redis 等；书中讲的主要是这种 |
| **语义缓存** | 响应 | 输入的嵌入与历史问题足够接近 | GPTCache 等 |
| **Prompt/前缀缓存** | KV cache（前缀的注意力计算） | 请求前缀与之前相同 | 厂商提供的 prompt caching（2024 年下半年起主流厂商陆续支持） |
| **嵌入缓存** | 文档/查询的向量 | 文本一致 | 自建；RAG 系统常见 |

- **语义缓存要小心**：问题相近 ≠ 答案相同。“iPhone 15 多少钱”和“iPhone 16 多少钱”嵌入距离很近但答案完全不同。阈值设松了返回错误答案，设严了命中率极低。建议只在**答案稳定、问题表述多样**的场景（FAQ）使用，并加上“关键实体一致”的硬约束。
- **前缀缓存改变了 Prompt 的写法**：它要求**稳定内容在前、动态内容在后**（系统提示 → 工具定义 → 知识资料 → 历史对话 → 当前问题），并且尽量让资料内容稳定，否则缓存失效。这是成书后“上下文结构”多出来的一个新约束，与 1.5 相辅相成。
- **缓存与护栏的联动**是书中很妙的点：缓存的不只是“答案”，还是“**已通过审查的状态**”。这在合规敏感场景里比省钱更有价值。
- **缓存失效策略**：知识更新（价格变了）需要主动失效——按来源文档的版本号生成缓存键是最简单可靠的做法。

### 什么时候微调

**【原文】** 有些任务即使 Prompt 设计得再巧妙也做不到。如果经过大量 Prompt 工程后系统离“可靠、高质量”还很远，那么可能需要针对任务微调模型。两个成功案例：

- **Honeycomb 的自然语言查询助手**：起初把“编程手册”和 n-shot 示例放进 Prompt，效果尚可；微调后模型在**领域特定语言的语法和规则**上表现更好。
- **ReChat 的 Lucy**：模型需要生成一种**结合结构化与非结构化数据的特定格式**供前端渲染，微调是一致工作的关键。

但微调有显著成本：标注数据、训练与评估模型、最终还要自托管。所以要想清楚前期投入是否值得。**如果 Prompt 能让你走到 90%，微调可能不值得。** 若决定微调，可以用**合成数据**或在开源数据上**自举**，以降低人工标注成本。

**【扩展】**

- **什么时候微调（行为问题）**：严格的输出格式/DSL、品牌语气、固定的推理模式、把大模型的能力蒸馏到小模型以降低延迟和成本、缩短 Prompt（省 token）。
- **什么时候不微调**：加新知识（→ RAG，见 2.3）、任务频繁变化、没有几百上千条高质量样本、没有能力维护自托管基础设施。
- **微调前的检查清单（我的总结）**：
  1. Prompt 和 RAG 都已尝试并到达瓶颈？
  2. 已有 ≥ 几百条（最好上千）真实、高质量的输入—输出样本？
  3. 评测集已就位（否则无法判断微调是否真的更好）？
  4. 失败模式是“不会做”而不是“不知道”？
  5. 有能力承担后续的模型运维（版本、回滚、监控）？
- **技术选择**：PEFT 方法（如 LoRA / QLoRA）让微调门槛大幅降低，单张消费级/单台工作站即可完成；蒸馏出一个 7B 级别的小模型做单一任务，常常比调用旗舰 API 更快更便宜。
- **合成数据路线**：用旗舰模型基于真实输入生成输出，人工抽检合格后作为训练数据；或“Prompt 在前、微调在后”——把长 Prompt 的行为蒸馏进模型（Prompt brevity）。

## 评估与监控（Evaluation and Monitoring）

**【原文】** LLM 的输入输出是任意文本，任务多种多样，所以评估是个雷区。但严谨而有思考的评估是关键——OpenAI 的技术负责人亲自参与评估工作、对单个 eval 给反馈，这并非巧合。

对 LLM 应用评估有多种视角：它就像单元测试，或者更像可观测性，或者只是数据科学。**作者发现这些视角全都有用。**

**【扩展】** 这三种视角对应评估的三个时间尺度，实践中应当三者都有：

| 视角 | 时间尺度 | 例子 | 失败的后果 |
|---|---|---|---|
| 单元测试 | 每次改 Prompt/模型时 | 断言、回归测试 | 改动引入回归而无人察觉 |
| 可观测性（监控） | 线上持续 | 用户反馈、拒答率、护栏触发率 | 数据漂移、模型供应商悄悄变更 |
| 数据分析 | 周期性 | 错误分析、按切片看指标 | 不知道该优先改什么 |

### 用真实的输入/输出样本建立少量断言式单元测试

**【原文】** 从生产中抽取输入/输出样本建立单元测试（即断言），对输出的期望**至少基于三个标准**。三个这个数字看似随意，但作为起点是实用的；**如果少于三个，可能说明任务定义不够清晰，或者太开放（如通用聊天机器人）。** 任何对流水线的改动（改 Prompt、通过 RAG 加新上下文等）都应触发这些测试。

起步建议：
- 从“所有回复都必须包含/不得包含某些短语或观点”的断言开始；
- 检查字数、条目数、句子数是否落在某个区间；
- 对于其他生成任务，断言形式会不同。**执行评估（execution-evaluation）** 是评估代码生成的有力手段：运行生成的代码，检查运行时状态是否满足用户请求。例如用户要求生成函数 `foo`，那么执行后 `foo` 就应该可调用。难点在于 Agent 生成的代码经常让运行时状态与目标代码略有不同，有效的做法是把断言“放宽”到**任何可行答案都必须满足的最弱假设**；
- **吃自己的狗粮（dogfooding）**：按客户的使用方式使用产品，既能发现真实数据上的失败模式，又能提供可转化为 eval 的生产样本。

**【扩展】一个断言式测试的示例（会议纪要，我的写法）：**

```python
def test_summary_assertions(sample):
    out = run_pipeline(sample.transcript)
    # 1. 必须包含原文中出现的每个负责人姓名
    for owner in sample.expected_owners:
        assert owner in out
    # 2. 不得出现原文中不存在的人名（幻觉守卫）
    assert not has_unknown_person(out, sample.transcript)
    # 3. 结构约束：恰好 N 条待办，每条带负责人
    todos = parse_todos(out)
    assert len(todos) == sample.expected_todo_count
    assert all(t.owner for t in todos)
    # 4. 长度约束
    assert 80 <= count_words_cn(out) <= 250
```

**补充要点：**
- “至少三个标准”背后的逻辑是：**一个只能写出一条断言的任务，大概率是你还没想清楚它到底要什么。** 这其实是需求澄清工具，而不只是测试工具。
- **“放宽到最弱假设”的示例**：任务“写一个函数，返回列表中第二大的数”。不要断言函数名必须叫 `second_largest`，只断言“存在一个函数，调用后返回正确值”。
- **执行评估与 HumanEval**：OpenAI 的 HumanEval（[Chen et al., 2021](https://arxiv.org/abs/2107.03374)）用的就是 pass@k——每个问题生成 k 个候选，只要有一个通过单元测试即算通过。这与 AlphaCodium 的 pass@5 是同一口径。注意 **pass@1（平均表现）与 pass@k（最好情况）是两个完全不同的指标**，报告时不要混用。
- **样本从哪来**：dogfooding 是冷启动最好的来源；上线后则是用户的负反馈点（点踩）、人工接管记录、护栏拦截记录。建议把这做成闭环：线上问题 → 标注 → 进入评测集 → 回归保护。
- **单元测试的局限**：它只能守住“已知失败模式”，无法告诉你平均质量。所以它需要和 4.2 的成对比较配合——一个管底线，一个管趋势。

### LLM-as-Judge 有点用，但不是银弹

**【原文】** 用强 LLM 评估其他 LLM 的输出，有人对此持怀疑态度（作者中有几位起初也是坚定的怀疑者）。但实现得好时，LLM-as-Judge 与人类判断有不错的相关性，至少能帮助建立“新 Prompt 或新技术可能表现如何”的先验。**当做成对比较（对照组 vs. 实验组）时，LLM-as-Judge 通常能选对方向，虽然输赢的幅度可能是有噪声的。**

建议：
1. **用成对比较**：不要让模型对单个输出按李克特量表打分，而是给出两个选项让它选更好的，结果更稳定。
2. **控制位置偏差**：选项顺序会影响判断。每对比较做两次，交换顺序。**注意交换后把胜负归到正确的选项上！**
3. **允许平局**：两个选项可能同样好，允许宣布平局，不要被迫选边。
4. **使用思维链**：先解释再给结论，可提高可靠性。附带好处是可用更弱、更快的模型达到类似效果；因为这部分流水线通常是批处理，CoT 的额外延迟不是问题。
5. **控制回复长度**：LLM 偏好更长的回复，确保成对的回复长度相近。

一个特别强大的应用是**回归检查**：如果记录了生产结果，可以用新的 Prompt 策略重跑这些样例，用 LLM-as-Judge 快速评估新策略在哪里可能吃亏。

作者展示了一个简单有效的方法：记录模型回复、评判者的批评（CoT）和最终结论，然后与利益相关者一起审查，找出改进点。**三轮迭代后，人与 LLM 评判的一致率从 68% 提升到 94%。**

但 LLM-as-Judge 不是银弹：语言的一些微妙之处，即使最强的模型也无法可靠评估。传统分类器和奖励模型可以达到更高准确率，且成本与延迟更低。对于代码生成，LLM-as-Judge 弱于执行评估这类更直接的策略。

**【扩展】**

**① 偏差不止书中说的两种。** Zheng 等人在 MT-Bench / Chatbot Arena 的工作（[Zheng et al., 2023](https://arxiv.org/abs/2306.05685)）系统记录了：

| 偏差 | 表现 | 缓解 |
|---|---|---|
| 位置偏差 | 偏好某个位置的选项 | 交换顺序做两次 |
| 冗长偏差 | 偏好更长的回答 | 长度配对；在评分标准里写明“简洁是优点” |
| **自我增强偏差** | 偏好自己（或同家族）生成的文本 | **评判者与被评者来自不同模型家族** |
| **有限的推理评分能力** | 难以判断需要复杂推理的数学/编程题 | 这类任务改用执行评估或规则校验 |

自我增强偏差是书中未提但非常重要的：**别用 GPT 评 GPT、用 Claude 评 Claude。**

**② “换家族”还不够：合成数据的闭环风险。** 如果评测集本身是由模型 A 生成的，再由模型 A（或近亲）打分，你测到的更接近“系统与自身的一致程度”。生成器与评判者也应尽量分离，并且定期用人工标注校准。

**③ 去偏后的成对比较流程（可直接照做）：**

```python
def pairwise_debiased(question, a, b):
    r1 = judge(question, a, b)   # A 在前
    r2 = judge(question, b, a)   # 交换位置
    winner_r1 = r1.winner                   # "A" 或 "B" 或 "tie"
    winner_r2 = "A" if r2.winner == "B" else "B" if r2.winner == "A" else "tie"
    return winner_r1 if winner_r1 == winner_r2 else "inconsistent"
```

两次结果不一致的比例本身就是一个有用的指标——它反映评判者的噪声水平。

**④ 68% → 94% 的方法论才是重点**：这个数字的具体值不重要，重要的是方法——**记录评判理由 → 与人一起审查 → 改评分标准 → 重测**。LLM-as-Judge 是一个需要“训练”的系统，评分标准（rubric）就是它的训练数据。

**⑤ 什么该交给规则，什么该交给 LLM？** 能写成代码的不要交给 LLM：格式校验（JSON Schema）、引用是否存在、数值是否在范围内、代码能否运行。LLM-as-Judge 留给真正主观的维度：相关性、语气、有用性。这与书中“传统分类器更准更便宜”是同一意思。

**⑥ 成书后的新趋势：Agent-as-a-Judge（2024 年底起）**。让评判者不只“读”，还能“做”——执行代码、搜索核实事实、打开引用链接——再综合判断。这本质上是把执行评估和 LLM-as-Judge 结合起来，回应了“LLM Judge 缺少外部验证”的短板。

**⑦ “方向对、幅度噪声大”的实践含义**：成对比较适合做 A/B 决策（哪个更好），不适合做精细的分数比较（提升了 3.2 分还是 3.5 分）。报告时用胜率而不是分差。

### 评估生成内容的“实习生测试”

**【原文】** 把语言模型的**完整输入**（包含上下文）原样交给一个相关专业的普通大学生作为任务，他/她能成功吗？需要多久？

| 回答 | 诊断 | 对策 |
|---|---|---|
| 不能，因为缺少必要的知识 | 上下文信息不足 | 想办法丰富上下文（RAG、加资料） |
| 不能，且无法通过改进上下文解决 | 任务超出了当代 LLM 的能力 | 缩小任务范围或放弃 |
| 能，但要花很久 | 任务太复杂 | 降低复杂度：可拆分吗？某些部分可以模板化吗？ |
| 能，而且很快 | 模型的问题 | 深入数据：模型哪里做错了？失败有规律吗？让模型在回答前后解释自己，建立它的“心智模型” |

**【扩展】**

- 这是本章我最推荐的工具，原因是它**不需要 ML 知识，也不需要跑实验**，只需要一个愿意认真读你 Prompt 的人。它把“模型行不行”这个模糊问题转化为“任务定义清不清楚”这个可操作的问题。
- 它与软件工程里的“新人心智测试”同构：如果一个新人拿着这份“需求文档”无从下手，那不是新人的问题，是文档的问题。
- **实操建议**：找一位懂业务但没参与项目的同事，把完整 Prompt 给他，**不给任何口头补充**，让他(1) 复述任务，(2) 试着做一条，(3) 说出他卡在哪。他的回答会直接告诉你上下文缺什么、结构哪里混乱。
- **与前文的连接**：
  - “丰富上下文” → 1.5 精雕上下文、第 2 节 RAG；
  - “任务可拆分” → 1.4 拆小 Prompt、3.1 多步流程；
  - “模板化” → 3.2 确定性工作流；
  - “模型哪里做错” → 4.1 断言测试，以及[第 2 章](/posts/llm-year-02/) 1.2 的错误分析。

**补充例子**：Prompt 要求“根据政策文档判断这封客户邮件是否需要升级处理”。实习生读完说：“我能判断，但文档里没说‘威胁要在社交媒体曝光’算不算需要升级。”——这就是上下文缺口的精确定位，回去补一条规则和两个示例即可。

### 过度强调某些评测会损害整体表现

**【原文】**

> 当一个度量成为目标，它就不再是好的度量。——古德哈特定律

反例是 **大海捞针（NIAH）** 评测。它把一句特定的话插进一篇重复 Paul Graham 文章的长文档，然后让模型复述那个“魔法数字”。它帮助量化了上下文变大后的召回能力，但被过度强调了——成了 Gemini 1.5 报告的图 1。有些模型召回近乎完美，但 NIAH 是否反映了真实应用所需的推理和召回能力是存疑的。

更实际的场景：给一小时的会议纪要，模型能否总结关键决策和下一步，并**正确地把每条事项归属到对应的人**？这超越了死记硬背，还涉及理解复杂讨论、识别相关信息、综合摘要。

作者给了一个“实用版 NIAH”的例子：用医患视频通话的文字记录，询问患者的用药情况——召回率约 **80%**；同时插入一句随机的“完美披萨的秘密配料”——召回率只有 **30%**。

此外，过度强调 NIAH 还可能**降低**抽取和摘要任务的表现：模型被微调得对每句话都高度关注，于是开始把无关细节和干扰项也当成重要内容，纳入最终输出。

这一点同样适用于其他评测和用例。例如摘要：强调事实一致性 → 摘要变得不那么具体（因此更不容易不一致），但可能不那么相关；强调文采和流畅 → 更多华丽的营销式语言，可能引入事实不一致。

**【扩展】**

- **NIAH 的问题究竟在哪？** 它测的是“精确字符串匹配后的复制”，不需要理解。而这恰恰是 LLM 最擅长的模式匹配之一。与本书同期的 RULER（[Hsieh et al., 2024](https://arxiv.org/abs/2404.06654)）和之后的 NoLiMa（2025）都印证了：**把字面捷径去掉之后，各模型的长上下文成绩大幅下滑。**
- **披萨配料的 30% 是个好例子**：同一个模型、同一篇长文档，只因“这句话在语义上与任务无关”，召回就掉了一大截。这说明**真实场景的干扰项不是随机的，而是看起来像答案的东西**。设计评测时要故意放“近似答案”（similar distractors）。
- **“过度关注 → 干扰项进摘要”的机制**：这是训练目标与评测目标错配。优化召回 → 模型学到“尽量多包含”→ 摘要任务里就成了“什么都往里塞”。这与 Goodhart 定律是一回事：**你奖励什么，就得到什么，包括它的副作用。**
- **多目标评测的实用建议**：摘要至少要同时看 (1) 事实一致性，(2) 覆盖度/相关性，(3) 简洁性。任何一项单看都会被钻空子。把三者做成三个独立指标并设最低门槛（任一不达标即失败），而不是加权求和——加权求和会让某一项的极端值掩盖另一项的崩坏。

### 简化标注：二元任务或成对比较

**【原文】** 对模型输出提供开放式反馈或李克特量表评分，认知负担很重，收集的数据噪声更大（评分者之间差异大），用处更小。更有效的做法是**简化任务、降低认知负担**。两种有效形式：

- **二元分类**：让标注者做“是/否”判断——摘要与原文事实一致吗？回复相关吗？含毒性吗？与李克特量表相比，二元判断更精确、评分者一致性更高、吞吐更高。DoorDash 就是用一棵“是/否”问题树为菜单条目打标签的。
- **成对比较**：给出一对回复，问哪个更好。因为说“A 比 B 好”比给 A 或 B 单独打分容易，所以标注更快更可靠。Llama 2 的作者之一 Thomas Scialom 在一次 meetup 上确认：成对比较比收集监督微调数据（如手写回复）更快更便宜——**前者每单位 3.5 美元，后者 25 美元。**

**【扩展】**

- **为什么李克特量表噪声大？** “4 分和 5 分的区别是什么”在不同人脑子里完全不同；即使同一个人，在不同时间、看到不同顺序的样本时标准也在漂移（锚定效应）。而“A 和 B 哪个好”是一个**相对判断**，不需要维持一个绝对标准。
- **一致性的度量**：用 **Cohen's Kappa（κ）** 等机会校正的一致性指标来看标注质量，而不是简单的一致百分比。二元任务还要看标注指南写得清不清楚——κ 低通常是指南的问题，不是标注者的问题。
- **成本换算的实践含义**：如果成对比较的成本是写回复的 1/7，那么做“偏好数据”（DPO/RLHF 用的 preference data）比做“监督微调数据”便宜得多。但要记住二者用途不同：偏好数据训练“哪种更好”，SFT 数据训练“该长什么样”。
- **三元/二元之外的折中**：有时你确实需要分级（比如“严重/轻微/无”），可以用**决策树式的二元问题**（DoorDash 的做法）：先问“有无问题？”→ 有 → “是否严重？”。每个节点仍是二元判断，整体却能给出多级标签。
- **中文场景补充**：中文标注要特别注意“事实一致”的判断——中文表达灵活（同义替换、语序变化、省略主语），标注指南里要给足正反例，否则 κ 会被“表达不同但意思相同”的情况拉低。

### （无参考的）评测与护栏可以互换使用

**【原文】** 护栏用于拦截不恰当或有害内容，评测用于衡量输出的质量和准确性。对于**无参考评测**（reference-free evals）而言，它们可以看作同一枚硬币的两面。无参考评测不依赖“黄金”参考答案（如人写的答案），仅基于输入 Prompt 和模型回复就能评估质量。

例子：摘要评测只需输入文档即可评估事实一致性和相关性。如果摘要得分差，可以选择不展示给用户——这就是把评测用作护栏。同理，无参考的翻译评测不需要人工参考译文，同样可用作护栏。

**【扩展】**

- **“同一枚硬币的两面”这个洞察的工程价值**：写一次无参考评测器，可以在两个地方使用——离线批量评测（出报告）与在线实时拦截（做决策）。不要写两套。
- **现成的工具**：摘要事实一致性有 SummaC（[Laban et al., 2022](https://arxiv.org/abs/2111.09525)）这类基于自然语言推理的评测器；幻觉检测有 SelfCheckGPT（[Manakul et al., 2023](https://arxiv.org/abs/2303.08896)）——对同一输入采样多次，看各次答案是否相互矛盾；无参考机器翻译质量估计有 COMET-QE 一类模型。
- **确定性的幻觉检测**：书中在 4.8 提到，当 RAG 输出是结构化的并标明引用了哪条资料时，可以**机械地**验证“引用的内容是否真的出自该资料”（字符串包含、数值比对、NLI 模型）。这是最便宜、最可靠的一类护栏，应优先实现。
- **三种“不通过”的处理**：拦截不展示 / 带提示降级展示（“以下信息可能有误”）/ 触发重新生成。要针对不同失败类型设定不同策略，而不是一刀切。

### LLM 在不应该输出时也会输出

**【原文】** 一个关键挑战：LLM 常常在不应该输出的时候照样输出。后果可能是无害但无意义的回答，也可能是毒性或危险内容。例子：要求从文档中抽取特定属性，模型会**自信地返回根本不存在的值**；或者因为上下文里有非英文文档，模型就用其他语言回答。

虽然可以让 Prompt 要求模型返回“不适用”或“未知”，但这不是万无一失的。即使有对数概率（log probs），它们也是输出质量的糟糕指标：log prob 表示 token 出现的可能性，但不代表生成文本的正确性；指令微调后的模型被训练成“对查询给出连贯回答”，其 log prob 可能**校准得很差**。高 log prob 说明流畅连贯，不说明准确或相关。

因此，仔细的 Prompt 工程能帮一些忙，但要用**稳健的护栏**来补充——检测并过滤/重新生成不理想的输出。例如 OpenAI 提供内容审核 API，能识别仇恨、自残、性相关等不安全回复；检测个人身份信息（PII）的包也很多。护栏的一个好处是与具体用例无关，可广泛应用于某一语言的所有输出。另外，**借助精确检索，当没有相关文档时，系统可以确定性地回答“我不知道”。**

一个推论：LLM 也可能在**应该输出时不输出**。原因从 API 供应商的长尾延迟，到输出被内容审核过滤器拦截，不一而足。因此要持续记录输入和（可能缺失的）输出，用于调试与监控。

**【扩展】**

- **这是整章最重要的“世界观”**：**LLM 是一个“总是有话说”的系统，它的默认行为不是“我不知道”。** 所有的抽取、结构化、RAG 应用都必须显式地处理“空”的情况。
- **为什么抽取任务特别严重？** 抽取 Prompt 通常隐含“请填满这个 Schema”，而 Schema 里的每个字段在语法上都期待一个值。模型倾向于“完成任务”而不是“留空”。缓解：在 Schema 中把字段设为可空并给出 `null` 示例；在指令中说明“若未提及请填 null”；并在 few-shot 示例里**刻意包含“字段缺失→null”的例子**（否则示例本身就在暗示“每个字段都有值”）。
- **拒答的三层防御**：
  1. **检索层（最确定性）**：RAG 召回分数低于阈值 → 直接走“未找到”分支，根本不调模型；
  2. **指令层**：明确允许“不知道”，并给出示例；
  3. **输出层**：校验引用是否存在、字段值是否真的在原文中出现。
- **关于校准**：书中说 log prob 校准差，这点有研究支持。对指令模型而言，更可靠的做法是**用行为而非概率来探测不确定性**——多次采样看一致性（SelfCheckGPT 的思路）、让模型给出引用再验证、或者训练一个小的“正确性分类器”。
- **“该输出时不输出”常被忽视**：线上突然出现大量空回复，可能原因是：模型提供商的过滤器误拦、JSON 解析失败（模型输出了多余的文字）、超时。监控要能区分“模型拒答”“护栏拦截”“技术故障”三种空。
- **成书后的变化**：2024 年下半年起，厂商开始把“知道何时说不知道”作为明确的训练目标（如 OpenAI 的 SimpleQA 测试集把“正确拒答”作为指标之一），模型的拒答行为整体变好了。但**在抽取和结构化任务上，“填满 Schema”的倾向依然存在**，防御不能省。

### 幻觉是个顽固的问题

**【原文】** 与内容安全、PII 这些受到大量关注因而很少发生的缺陷不同，**事实不一致**顽固且更难检测。它更常见，**基线发生率在 5%～10%**；而且据作者从 LLM 供应商那里了解到的，即使在做摘要这样的简单任务上，**也很难降到 2% 以下**。

应对方法是上下游结合：
- **上游（Prompt 工程）**：CoT 等技巧让模型先解释推理再给结果，有助于减少幻觉；
- **下游（事实不一致护栏）**：评估摘要的事实性，过滤或重新生成幻觉。
- 在某些情况下，幻觉可以**确定性地检测**：使用 RAG 检索到的资源时，如果输出是结构化的并指明了引用的是哪些资源，就应该能人工验证它们确实来自输入上下文。

**【扩展】**

- **5%～10% 这个数字的份量**：如果一个客服机器人每天回答 1 万个问题，那就意味着每天 500～1000 个带事实错误的回答。**这是“为什么 LLM 产品不能没有护栏与人在回路”的定量依据。** 成书后模型能力大幅提升，幻觉率在不少任务上有明显下降，但“摘要中的细微事实错误（数字、日期、人名、否定词）”和“引用对了、解读错了”仍是难点。
- **幻觉的三个来源，对应三种对策**：

| 来源 | 表现 | 对策 |
|---|---|---|
| 知识缺失 | 模型不知道，于是编 | RAG + 允许说“不知道”（第 2 节、4.7） |
| 上下文被忽略/误读 | 资料里有，但用错了 | 精雕上下文（1.5）、强制引用（1.2.3）、结构化 chunk |
| 推理/抽取错误 | 对牛头不对马嘴，数字张冠李戴 | 具体化 CoT（1.2.2）、多步流程（3.1）、确定性校验（4.6） |

- **按成本排序的幻觉检测阶梯（我的总结）**：① 确定性检查（数字、日期、人名是否在原文出现）→ ② NLI 模型判断“原文能否推出这句话”（SummaC）→ ③ LLM-as-Judge 带引用核查 → ④ 人工抽检。先做①，它最便宜，能抓住大部分“明显编造”。
- **“重新生成”的注意事项**：检测到幻觉后重新生成，第二次未必更好；应记录重生成率，它上升说明上游出了问题（检索质量下降或文档更新）。
- **分场景设定阈值**：闲聊类产品对幻觉容忍度高，医疗/法律/财务场景几乎为零。后者应当默认“无引用不回答”，并由人复核。

## 书里说得不够或可以商榷的

成书两年多以后，各节的变化已经写在上面的【扩展】里，逐条的现状核对放在[第四篇](/posts/llm-year-04/)。这里只记本章书里没讲到、说得不够，或者我觉得可以商榷的地方：

1. **“n ≥ 5”是经验值而非定律**。示例的数量远不如**示例的质量与分布**重要。5 个精心挑选的边界示例胜过 30 个雷同的简单示例。推理模型对示例的依赖更低，示例还会占用推理预算；但示例在“定义格式与边界情况”上仍不可替代。
2. **“至少三个标准”** 对开放式生成任务（头脑风暴、创意写作）并不适用；这类任务更适合成对比较 + 人工品味评审。
3. **“优先确定性工作流”** 与 **“Agent 的自主性”** 之间存在真实的张力，书中偏向一边是合理的，但读者应知道这是**风险偏好**的选择而非技术优劣的绝对判断。
4. **LLM-as-Judge 68% → 94%** 是单一案例的数字，不应作为预期。真正可迁移的是“记录评判理由 → 人工审查 → 改 rubric”这个流程。
5. **temperature 的讨论** 略显简略，没有提到 temperature 对长输出的累积质量损害，以及它与 top-p 的相互作用。
6. **“每个模型家族有格式偏好”今天已不那么要紧**：各家模型对 XML 和 Markdown 都能较好处理；更重要的是**用明确的边界标签隔离不可信数据**（防注入）。
7. **评估部分缺少对采样方差的讨论**：同一个 Prompt 跑两次结果不同，评估必须重复采样并报告均值与置信区间；评测集的**污染**（测试题在训练数据里）也需要警惕。
8. **Agent 部分缺少对工具调用可靠性的讨论**：工具选错、参数填错是现代 Agent 最主要的失败来源之一，需要专门的工具调用评测。
9. **推理模型的中间过程看不全**：不少推理模型对外只给推理摘要，“把中间产物暴露出来再做断言”这条路在它们身上要打折扣。
10. **没涉及的话题**：多模态、提示注入的系统性防御、模型供应商变更导致的回归、成本/延迟作为一等指标（这部分在[第 2 章](/posts/llm-year-02/)）。

## 贯穿全章的底层思想（提炼）

读完这一章，我把散落的技巧归纳为**七条原则**：

1. **先便宜后昂贵**：Prompt → 示例 → 结构化 → 多步 → RAG → 缓存 → 微调。每一层到顶之前不要上下一层。
2. **拆小**：一个 Prompt 只做一件事；一个任务拆成多个步骤；一个流程拆成多个可评测的单元。拆小是评测、缓存、确定性执行、可观测的前提。
3. **让隐性的东西显性化**：CoT 的草稿、结构化输出、生成的计划、评判者的理由——凡是模型“脑子里”的东西，都尽量让它写出来，这样才能检查。
4. **用确定性包裹概率性**：Schema 校验、执行评估、引用核验、缓存、确定性工作流、阈值拒答——都是用代码的确定性去框住模型的不确定性。
5. **上下文是稀缺资源**：每个 token 都有成本（钱、延迟、注意力稀释）。凿掉多余的，结构化保留的，把重要的放在开头和结尾。
6. **没有评测就没有迭代**：所有优化都依赖能测出变化。评估既是测试（守底线），也是监控（看趋势），也是分析（找方向）。
7. **模型总是有话说**：默认它不会说“不知道”，默认它会编造缺失的值，默认每一步都可能失败——所以要有“不知道”的出口、要有护栏、要有恢复机制。

还有一个“人”的原则，藏在 3.2 那句“带过初级工程师的人”里：**像对待聪明但没有上下文、也不会主动说“我不懂”的新同事一样对待 LLM**——目标清晰、步骤具体、给出必要的资料、规定输出格式、允许它说不知道、并且检查它的产出。

## 落地检查清单

把本章的建议压缩成一份可以直接对照的清单：

**Prompt**
- [ ] 是否从 Prompt 开始，而不是从微调/Agent 框架开始？
- [ ] 示例是否 ≥ 5 个、分布是否与真实数据一致、标签是否均衡、顺序是否打乱？
- [ ] CoT 是否写具体了步骤？对推理模型是否反而应该少写？
- [ ] 是否告诉模型“优先使用资料、注明引用、资料不足时明说”？
- [ ] 输入是否结构化（Schema/标签）？输出是否结构化并可校验？
- [ ] 是否把最终 Prompt 导出来，放在空白页上完整读过一遍？
- [ ] 一个 Prompt 是否只做一件事？

**RAG**
- [ ] 是否有 BM25 作为基线？是否做了混合检索？
- [ ] 是否测了 MRR/NDCG？是否做了“打乱实验”？
- [ ] chunk 是否带元信息（来源、日期、标题）？是否有重排？
- [ ] 新知识是否用 RAG 而非微调？权限是否按租户隔离？
- [ ] 是否评估过“全量塞长窗口” vs “RAG” 的成本/延迟/准确率？

**工作流**
- [ ] 任务是否拆成了小步骤？每步的失败是否可定位？
- [ ] 多少步骤是模型做的、多少是代码做的？端到端成功率估算过吗（pⁿ）？
- [ ] 高风险操作是否需要审批？计划是否可被用户看到？
- [ ] 是否实现了精确缓存？是否利用了前缀缓存（稳定内容在前）？
- [ ] 微调前是否确认了 Prompt 已到瓶颈、数据足够、评测就位？

**评估与监控**
- [ ] 是否有基于真实样本的断言式测试（≥ 3 条标准）？每次改动是否自动触发？
- [ ] LLM-as-Judge 是否成对、交换位置、允许平局、用 CoT、控制长度、换模型家族？
- [ ] 是否做过“实习生测试”？
- [ ] 是否有多个指标并设最低门槛，而非单一指标？
- [ ] 标注是否简化为二元/成对？是否测了 κ？
- [ ] 是否有无参考评测兼做线上护栏？
- [ ] 抽取任务的空值是否真的返回 null？“不知道”是否有出口？
