第 1 章讲“怎么把一个 Prompt 调好”，第 3 章讲“公司该不该做、怎么做才不被淘汰”。第 2 章夹在中间，讲的是**真正落地时的运营问题**：系统上线后怎么不烂、团队怎么组织、产品怎么设计。

作者开篇引用了一句“据说是很多领袖说过”的话，大意是**外行谈战略与战术，内行谈运营**。这句话点出本章的视角：战术层看到的是一堆“独一无二”的技术问题，运营层看到的是**可以修复的组织性机能失调**——问题反复出现，不是因为技术难，而是因为流程缺了。

本章按四个问题域展开：

| 问题域 | 要回答的问题 | 核心答案（一句话版） |
|---|---|---|
| **数据** | 多久、怎样审查 LLM 的输入输出？怎样衡量并减少开发—生产偏差？ | 每天看样本；把偏差分成结构性和内容性两类来监控 |
| **模型** | 如何把模型集成进技术栈？如何做版本管理与迁移？ | 结构化输出；Prompt 不可移植；固定版本 + 影子流水线；选够用的最小模型 |
| **产品** | 设计何时介入？如何设计带人在回路的 UX？如何排优先级、校准风险？ | 尽早让设计参与；把反馈做进 UX；“最小可爱好产品”；按用例定标准 |
| **人** | 招谁、何时招？如何建立实验文化？流程重要还是工具重要？ | 流程先于工具；持续实验；赋能所有人；“AI 工程师不是全部” |

一条暗线贯穿四部分：**LLM 应用是一个与外部世界持续耦合的系统**——用户在变（数据漂移）、供应商在变（模型更新）、产品形态在变（UX）、团队也在变（角色演进）。传统软件的运营假设是“部署后系统是稳定的”，LLM 应用恰恰相反。本章几乎所有建议都可以理解为对“不稳定”的回应。

## 数据（Data）

**【原文】** 正如食材质量决定菜品味道，输入数据的质量约束了机器学习系统的表现；输出数据则是判断产品是否奏效的唯一途径。**作者们所有人都紧盯数据，每周花好几个小时看输入输出**，以理解数据分布：它的众数、边界情况，以及模型对它理解的局限。

### 检查开发—生产偏差

**【原文】** 传统机器学习流水线里，一个常见的错误来源是“训练—服务偏差”（train-serve skew）：训练数据和线上遇到的数据不一样。LLM 可以不经训练直接使用，所以没有训练集，但一个类似的问题依然存在——**开发—生产数据偏差**：开发时测试系统用的数据，应当镜像系统上线后要面对的数据；否则线上准确率会受损。

作者把 LLM 的开发—生产偏差分成两类：

| 类型 | 含义 | 例子 |
|---|---|---|
| **结构性偏差**（structural） | 格式上的不一致 | 值是列表的 JSON 字典 vs. 直接是 JSON 列表；大小写不一致；错别字、句子残缺 |
| **内容性偏差**（content-based，或“语义”偏差） | 数据的含义或语境不同 | 用户讨论的话题变了，进入了模型没接触过的领域 |

结构性偏差会导致不可预测的表现，因为不同 LLM 是在特定格式的数据上训练的，而 **Prompt 对微小变化可能高度敏感**。

怎样监测：
- **简单指标**：输入/输出的长度、是否满足特定格式要求（JSON、XML）——直接追踪变化。
- **进阶漂移检测**：对输入/输出的嵌入做聚类，发现语义漂移——比如用户讨论的话题发生了转移。
- **留出集要保持“新鲜”**：测试改动（如 Prompt 工程）时，留出数据集要反映最近的真实交互。例如线上输入里错别字很常见，留出集里也应有。
- **数值之外还要看质量**：定期人工审阅输出——俗称“vibe check”——确认结果符合预期、仍然贴合用户需求。
- **把非确定性纳入检查**：对测试集里的每个输入把流水线多跑几次、分析全部输出，更容易抓住偶发的异常。

**【扩展】**

**① 为什么“训练—服务偏差”这个老概念对 LLM 仍然适用？**
LLM 应用的“训练集”其实是：Prompt 里的 few-shot 示例、开发者脑子里对“用户会怎么问”的想象、以及评测集。三者都在替模型“定义世界”。线上数据一旦偏离这个定义，模型的表现就会以你意想不到的方式崩坏。传统 ML 里这个概念早已是工程常识（Google 内部 ML 规则里有专门条目，ML Test Score 论文也把 train-serve skew 列为必测项），本书只是把它平移到 LLM 场景。

**② 结构性偏差为什么杀伤力大？——Prompt 格式敏感性有量化证据**
Sclar 等人（2023）发现，**只改变 Prompt 里示例的排列方式、字段名、分隔符**，同一模型在同一任务上的表现就可以出现大幅波动，方差很大（[Sclar et al., 2023](https://arxiv.org/abs/2310.11324)）。也就是说，LLM 对“格式”的敏感不是错觉。所以线上把 `{"tags": ["a","b"]}` 变成 `["a","b"]`、把全角引号换成半角、在末尾多一个空行——都足以让输出发生变化。

工程上的对策：**在边界处做规范化与校验**。所有进入 Prompt 的数据先过一层 Schema 校验与归一化（Pydantic / JSON Schema），而不是“拿到什么塞什么”。

**③ 漂移检测的常用度量（我的补充）**

| 目的 | 方法 | 说明 |
|---|---|---|
| 数值分布漂移（长度、语言比例、格式合规率） | PSI（群体稳定性指数）、KS 检验、Jensen–Shannon 散度 | 简单、可设告警阈值 |
| 语义漂移 | 输入嵌入 → 聚类（如 HDBSCAN）→ 观察新簇/簇占比变化；或与基线分布比较 MMD | 能发现“用户开始问新东西了” |
| 新意图/新主题 | 对最近 N 天输入做主题模型或 LLM 自动打标，对比基线 | 比 LLM-as-Judge 更便宜、更适合高频监控 |
| 偶发异常 | 同一输入重复采样（self-consistency） | 多次结果不一致本身就是“不稳定”的信号 |

**④ “非确定性”的补充**：即使 temperature 设为 0，多数服务也不保证确定性——原因来自批处理大小相关的 GPU 内核、MoE 路由、浮点累加顺序等（业界 2025 年开始讨论“批不变性”内核，但远未普及）。含义：**评测必须重复多次并报告均值/方差**；线上“偶尔崩”的问题要在开发环境复现，靠的就是多次重跑。

**⑤ RAG 与 Agent 场景下容易漏掉的偏差**

- RAG：开发时用的是“干净的测试语料”，线上索引里却有乱码、扫描件、过期文档、重复文档——**检索到的 chunk 本身就是输入的一部分**，它的质量漂移会直接变成模型输入漂移。
- Agent：工具返回的格式变了（API 升级、网页改版）——这是 Agent 应用最常见的线上事故来源之一。

**补充例子**：开发阶段测试“合同抽取”时，PDF 都是用 Word 导出的规范文本；上线后客户上传的是扫描件 OCR 结果，页眉页脚穿插在正文中，金额写成“人民币壹拾万元整”。模型输出不是结构错，而是抽错字段。这类问题在开发集里完全看不出来——它不是“模型不够强”，是输入分布变了。

### 每天看 LLM 的输入输出样本

**【原文】** LLM 是动态的、持续演化的。尽管零样本能力惊人、输出常令人愉悦，其失败模式却高度不可预测。对定制任务来说，定期看样本是建立“LLM 表现直觉”的必要途径。

**生产环境的输入输出对，就是 LLM 应用的“现地现物”（genchi genbutsu），无可替代。** 近来的研究显示，开发者对“什么是好/坏输出”的认知会随着看的数据增多而改变（即**标准漂移**，criteria drift）。开发者可以预先想出一些评估标准，但这些预定义标准往往不完整。例如开发过程中我们会改 Prompt 来提高好回复的概率、降低坏回复的概率——这个“评估、再评估、更新标准”的循环是必需的，因为不直接看输出，很难预测 LLM 的行为或人类的偏好。

管理方式：
- **记录输入输出**；
- **每天抽样查看**，快速识别新规律或失败模式；
- 发现新问题就**立刻为它写一条断言或评测**；失败模式定义的任何更新，也要反映到评测标准里；
- **“vibe check”是坏输出的信号，代码与断言把它们落地**；
- 这种态度必须**社会化**——例如把“审查/标注输入输出”加进值班轮换（on-call rotation）。

**【扩展】**

**① “现地现物”是什么？** 这是丰田生产方式里的“三现主义”（现场、现物、现实）之一：管理者必须亲自到现场看实物，而不是只读报表。作者借用它表达一个态度：**指标是二手的，样本是一手的。** 指标告诉你“变差了 3 个点”，只有样本能告诉你“为什么”。

**② 标准漂移出自哪里**：书里这句链的是 Shankar 等人 2024 年的 EvalGen 论文（[Shankar et al., 2024](https://arxiv.org/abs/2404.12272)）。他们发现，用户要先有标准才能给输出打分，可正是打分的过程让他们想清楚了标准，所以标准会在评估过程中不断变化，他们把这叫作“标准漂移”。这不是评估者的过错——**标准本来就是在接触数据的过程中才逐渐清晰的**。对 LLM 应用的含义：不要指望“一次性写出完美的评测标准”，把标准的迭代当成常态。

**③ “看数据”的正确姿势（我的流程建议）**

1. **抽样而非只看告警**：随机抽 20～50 条 + 专门抽“可疑”的（护栏触发、用户点踩、重试、超长输出）。只看告警会漏掉“沉默的错误”——用户没抱怨但答案是错的。
2. **带着问题看**：这条输出错了吗？属于哪一类错（检索错/理解错/格式错/拒答不当）？错在流程的哪一步？
3. **把错误分桶**：按失败类型归类，统计每桶数量。**优先修最大的桶**——这是错误分析（error analysis）的核心，比“看一百条然后凭感觉改 Prompt”有效得多。
4. **每个桶沉淀一条断言**：看数据 → 发现模式 → 固化为测试 → 回归保护。这就是第 1 章 4.1 的落地闭环。
5. **定期换人看**：不同的人会发现不同的失败模式；新人尤其能发现“老手已经习以为常”的问题。

**④ 日志该记什么**：请求 ID、完整最终 Prompt（拼接后的）、模型名与版本、采样参数、输出、工具调用轨迹、检索到的 chunk 及分数、延迟与 token 数、护栏结果、用户反馈。注意**脱敏与留存期限**——日志里有用户数据，留存政策要与合规一致。

**⑤ “加进值班轮换”的深意**：这意味着“看数据”不是算法工程师的副业，而是**运维职责的一部分**，和看监控大盘同等重要。谁值班，谁就要看当天的样本。否则“每天看数据”永远排在待办最后。

## 使用模型（Working with Models）

**【原文】** 有了 LLM API，我们可以依赖少数几家供应商的“智能”。这是好事，但这些依赖也带来了性能、延迟、吞吐、成本上的权衡。而且，过去一年里几乎每月都有更好的新模型发布，我们要准备好在旧模型被弃用时更新产品、迁移到新模型。本节分享的是使用“我们无法完全掌控、不能自托管的技术”的经验。

### 生成结构化输出，方便下游集成

**【原文】** 多数真实场景里，LLM 的输出会被下游应用通过某种机器可读格式消费：
- **Rechat**（房地产 CRM）：前端渲染小部件需要结构化回复；
- **Boba**（生成产品战略想法的工具）：需要带标题、摘要、可信度评分、时间跨度的结构化输出；
- **LinkedIn**：约束 LLM 生成 YAML，用来决定调用哪个技能，并提供技能参数。

这个模式是**波斯特法则**（Postel's law）的极端版本：对接收的东西宽松（任意自然语言），对发出的东西保守（带类型的机器可读对象）。作者因此认为它会非常持久。

当时的事实标准：调 API 用 Instructor，自托管模型用 Outlines。

**【扩展】**

**① 波斯特法则**：出自 Jon Postel 在 1980 年写的 TCP 规范（RFC 761），原意是“TCP 实现应当健壮：对输入宽容，对输出严格”。作者把它套到 LLM 上非常贴切：**自然语言进，类型安全出。** 这是 LLM 应用与传统软件的接口契约。

**② 为什么这个模式“会非常持久”？** 因为它把 LLM 的不可靠性**封装在一个可测试的边界内**：下游代码不需要理解自然语言，只需要处理一个对象；而对象可以校验、可以拒绝、可以重试。两年多后的今天，结构化输出已是各家 API 的原生能力，这恰恰证明了模式的持久。

**③ 结构化输出保证了格式，不保证语义。** 这是最常见的误解。Schema 校验通过只说明“字段齐全、类型对”，不保证内容正确：金额可能是编的，日期可能不在合理范围，枚举值虽然合法但选错了。所以要做**分层校验**：

```python
# 第 1 层：Schema 校验（格式）——由结构化输出/Pydantic 保证
# 第 2 层：业务规则校验（语义）——自己写
def validate(inv: Invoice, source_text: str):
    assert inv.total_cents >= 0
    assert inv.currency in {"CNY", "USD"}           # 枚举
    assert 2020 <= inv.issued.year <= 2030           # 合理区间
    assert inv.invoice_number in source_text          # 必须来自原文
    assert abs(sum(i.amount_cents for i in inv.line_items) - inv.total_cents) < 1  # 内部一致
```

第 2 层的失败率本身就是一个重要的质量指标。

**④ Schema 设计建议**：字段加描述；用枚举限制取值；必填与可空明确区分（对应第 1 章“不该输出也输出”——可空字段要允许 null）；嵌套不要太深；大任务拆成多个小 Schema。校验失败时把**错误信息回传给模型重试**往往有效，但设重试上限。

**⑤ 工具调用 / 函数调用就是结构化输出的特例**：LinkedIn 的“YAML 决定调用哪个技能”，在今天的术语里就是 function calling。2024 年后各家 API 统一了这个接口，Agent 浪潮的基础设施正是它。

### 跨模型迁移 Prompt 是件苦差事

**【原文】** 有时精心打磨的 Prompt 在一个模型上表现优异，在另一个上却一落千丈。这既发生在跨供应商切换时，也发生在同一模型跨版本升级时。

- **Voiceflow** 发现从 gpt-3.5-turbo-0301 迁移到 gpt-3.5-turbo-1106，意图分类任务掉了 **10%**（幸好他们有评测）。
- **GoDaddy** 观察到正向的趋势：升级到 1106 后，gpt-3.5-turbo 与 gpt-4 的差距缩小了。（悲观者也可以说 gpt-4 的领先优势被削弱了。）

所以，如果必须迁移，**预期投入远不止“换一下 API 端点”**；不要假设同一个 Prompt 会带来相近或更好的结果。可靠的自动化评测能帮你在迁移前后衡量任务表现，并减少人工验证的工作量。

**【扩展】**

**① 为什么 Prompt 不可移植？** 三个原因：
- **分词器不同**——同一句话在不同模型眼里是不同的 token 序列；
- **训练数据的格式分布不同**——Claude 训练时见过大量 XML，GPT 见过更多 Markdown，这决定了“哪种写法让模型更在行”；
- **指令微调的风格不同**——“服从指令”的边界、对否定词的处理、默认的回答长度，每个模型都有自己的性格。

**② 升级不总是进步**：Chen、Zaharia 与 Zou 在 2023 年研究了 ChatGPT 在数月内的行为变化，发现某些任务上表现随时间**变差**，且在模型名不变的情况下悄然发生（[Chen et al., 2023](https://arxiv.org/abs/2307.09009)）。Voiceflow 的 10% 是同一现象的工程版。**结论：“更新的版本更好”是一个假设，需要用评测证伪，而不是前提。**

**③ 迁移的工程纪律（我的补充，综合业界实践）**
1. **模型 ID 只存在一处配置**，而不是散落在代码里；
2. 先读供应商的迁移说明：被移除的参数、改变的默认值、分词与价格变化；
3. 在线上样本构成的“黄金集”上**新旧并跑**，比较成功率、格式合规率、拒答率、成本、延迟——**逐条读那些变差的样本**；
4. 先**删掉旧模型时代的 workaround**，再针对新模型加指令（否则是一层层补丁叠补丁）；
5. 灰度发布，保留一键回滚；
6. **微调过的模型有自己的问题**：基座退役，微调成果随之报废，必须在新基座上重做。

**④ 抽象层的取舍**：用统一网关/抽象库（如各类 LLM gateway）把模型 ID 从代码中抽出来，可以把“代码迁移”变成“配置变更”。但要清醒：**抽象层解决的是调用可移植，解决不了 Prompt 可移植。** 过度抽象还会屏蔽各家独有功能（缓存、工具调用细节）。建议抽象“路由与可观测”，不抽象“Prompt 与评测”。

### 给模型做版本管理并固定版本

**【原文】** 在任何机器学习流水线里，“改变任何东西就改变一切”。当我们依赖不是自己训练的 LLM 时更是如此——它们可能在**我们不知情的情况下改变**。

好在很多供应商提供“固定”（pin）具体版本的功能（如 gpt-4-turbo-1106），让我们使用特定的模型权重，保证不变。在生产环境固定版本，可以避免模型被替换后突发的行为变化——例如输出突然变得啰嗦，或其他未曾预料的失败模式——这类变化往往先表现为客户投诉。

另外，考虑维护一条**影子流水线**：镜像生产配置，但使用最新的模型版本。这可以安全地试验和测试新版本；一旦验证了新模型输出的稳定性与质量，就能有信心地更新生产环境的模型版本。

**【扩展】**

**① “改变任何东西就改变一切”**（CACE）出自 Sculley 等人关于 ML 技术债的论文：书里链的是 2015 年的 *Hidden Technical Debt in Machine Learning Systems*，这个说法最早见于他们 2014 年的论文。它说的是 ML 系统与传统软件的根本差异：在传统软件里，改 A 只影响 A；在 ML 系统里，改数据、改阈值、改依赖，全局都可能变。LLM 应用把这个特征放大了——**你连“改变”的知情权都没有**。

**② 固定版本的两个限制（书中未展开）**
- **固定不是永久的**：供应商会在若干个月后退役旧版本，你终究得迁移。所以固定版本买的是“时间”，不是“终局”——迁移能力必须常态化。
- **浮动别名是隐患**：`latest`、`preview`、不带日期的模型名都可能在你没部署的情况下变。**生产只用带明确版本号的 ID**，别名仅限开发环境。

**③ “影子流水线”在今天已经是成熟做法**，通常分三步：
1. **离线回归**：黄金集上跑新版本，与旧版本基线对比；
2. **影子流量**：把线上请求复制一份发给新模型，但**不返回给用户**（注意：不要产生副作用——对 Agent 只影子化只读部分，或把工具指向沙箱）；
3. **灰度发布**：5% → 25% → 100%，每步观察固定窗口，出问题一个开关回滚。

**④ 给“退役”配一个负责人**：订阅供应商的弃用公告，维护一张“模型清单 + 退役日期”表，指定谁负责。一句话：**没有负责人的退役日期，会以故障的形式被“发现”。**

**⑤ 把模型变更当作一次部署**：需要审批人、评测结果、回滚预案——就像上线代码一样，而不是“运维顺手改个参数”。

### 选择能完成任务的最小模型

**【原文】** 做新应用时，用最强大的模型很有诱惑力。但一旦确认任务在技术上可行，就值得实验一下更小的模型能否达到相近效果。

小模型的好处是更低的延迟与成本。虽然它较弱，但思维链、n-shot、上下文学习可以让小模型“超水平发挥”；针对任务微调也能提升表现。合在一起，**用小模型精心设计的工作流，常常可以匹配甚至超过单个大模型一次生成的质量，同时更快更便宜。** 作者举了一个坊间数据：Haiku 配 10-shot 胜过零样本的 Opus 和 GPT-4。长期来看，他们预期会看到更多“小模型 + 流程工程”作为质量、延迟、成本的最优平衡。

另一个例子是分类任务：**DistilBERT**（6700 万参数）是出奇强的基线；**4 亿参数的 DistilBART** 也是好选择——在开源数据上微调后，识别幻觉的 ROC-AUC 达到 **0.84**，超过多数 LLM，而延迟与成本不到它们的 **5%**。

重点是别忽视小模型。把大模型砸向每个问题很容易，但带着一点创意与实验，常常能找到更高效的解法。

**【扩展】两年多后回看，这一节的方向被验证了，但省钱的空间被单价下跌和缓存压缩了：小模型和路由仍有必要，却不再是最大的成本杠杆。**

**① 小模型强在哪、弱在哪（按任务形状分，而非按行业分）**

| 任务形状 | 例子 | 推荐档位 | 原因 |
|---|---|---|---|
| 分类 / 路由 / 意图识别 | 工单分类、审核、情绪 | 小模型（编码器或 7B 级）；少量样本可考虑 SetFit 等小样本方法 | 决策空间小、高并发、成本敏感 |
| 结构化抽取 | 发票、简历、表单 | 小到中型模型 + 严格 Schema（可微调） | 格式保证比推理更重要 |
| 有界摘要 / 格式转换 | 会议纪要、单文档摘要 | 小到中型模型 | 重活在检索与前处理，不在生成 |
| 多步规划、开放推理、广泛世界知识 | 调研、复杂代码、模糊判断 | 前沿模型 | 早期错误会在后续步骤中放大 |

**② 从“选一个模型”到“按步骤路由”**：业界目前常见的做法是**分层路由**——流程里大量简单、高频的步骤交给小模型，只把真正难的步骤升级到前沿模型；升级条件可以是规则（任务类型）、置信度、或输出未通过校验。这与本节“小模型加流程工程”的结论完全同向，只是走到了步骤粒度。

| 路由方式 | 成本（相对全用前沿） | 工程量 | 风险 |
|---|---|---|---|
| 全部用前沿模型 | 100% | 无 | 无（但贵、慢） |
| 规则路由 | 约 35%～50% | 低（数天） | 规则保守则很低 |
| 规则 + 置信度升级 | 约 20%～35% | 中（数周） | 需要监控质量 |

（表中的成本比例来自业界博客的经验数字，非受控实验，量级仅供参考。）

**③ 两个前提，缺一不可**
- **先有评测再换模型**：没有任务专属评测集，“小模型更差”只是感觉。经验之谈：团队对自己任务上哪个模型更好，判断错误的概率并不低，而且两个方向的错都有。
- **任务稳定后再优化**：还在探索任务该怎么做的阶段，用前沿模型；任务定义清楚后再下沉到小模型。否则你是在同时调试路由和任务。

**④ 为什么“编码器小模型”在分类上仍然能打？** DistilBERT（[Sanh et al., 2019](https://arxiv.org/abs/1910.01108)）把 BERT 缩小了 40%，保留了约 97% 的性能；DistilBART（[Shleifer & Rush, 2020](https://arxiv.org/abs/2010.13002)）用类似的办法压缩 BART。DistilBERT 是**双向编码器**；DistilBART 是编码器—解码器结构，但编码器部分同样是双向的。这类模型做“理解型”任务（分类、NLI）天然高效；而生成式 LLM 为了“通用”付出了巨大的推理代价，用在单一分类任务上是浪费。书中那个 0.84 的幻觉识别，本质是 NLI（判断“原文能否推出摘要”），正是这类模型的主场。

**⑤ 自托管的成本临界点**：小模型只有在流量足够大时才比 API 便宜——GPU 是固定成本，利用率低时省不了钱。经验上，月请求数达到数十万到百万级、且延迟敏感或有数据不出域要求时，自托管才划算；否则调用 API 的小档位更经济。

**⑥ 2026 年的补充**：开源小模型（7B～30B 级）的能力在两年里提升显著，加上推理框架的优化，“Llama/Qwen 级别 7B 模型 + 好的检索”在 RAG 问答上与前沿模型的差距已大幅缩小——因为这类任务的重活在检索。但这**不等于前沿模型不重要**：开放推理、多步规划、错误代价高的判断仍是它的领地。

**⑦ 中文场景**：中文小模型选择要看中文语料训练充分度、分词效率（中文 token 效率差异会影响成本）、工具调用能力；用自己业务数据做评测，不要看通用榜单。

## 产品（Product）

**【原文】** 新技术带来新可能，但做出好产品的原则是永恒的。即使第一次解决新问题，也不必在产品设计上重造轮子。把 LLM 应用开发建立在扎实的产品基本功上，才能真正为用户交付价值。

### 尽早且经常让设计参与

**【原文】** 有设计师会迫使你深入思考产品如何构建、如何呈现给用户。我们有时把设计师刻板化为“把东西变好看的人”，但除了界面，他们还会**重新思考用户体验如何改善，哪怕这意味着打破现有规则与范式**。

设计师尤其擅长**把用户的需求重新表述成不同的形式**——其中一些形式更容易解决，因而给 AI 留出更多或更少的机会。与许多产品一样，做 AI 产品应当围绕**待完成的任务**（job to be done），而不是围绕驱动它的技术。

要问自己：用户让这个产品为他们做的工作是什么？这个工作适合聊天机器人吗？适合自动补全吗？也许适合别的东西！去思考现有的设计模式，以及它们与“待完成的任务”的关系——这是设计师带给团队的宝贵资产。

**【扩展】**

**① “待完成的任务”（Jobs to Be Done）** 来自 Christensen 等人的思想（“奶昔实验”是经典案例）：用户“雇用”产品来完成某个任务，产品成功与否取决于它把任务完成得好不好，而不是它用了什么技术。套到 LLM 上：**用户不是想“和一个 AI 聊天”，而是想“把这件事做完”。** 聊天界面只是众多可能的“形态”之一，而且往往不是最优的。

**② 同一个任务的不同形态（我的例子）**：用户任务 = “把这段中文邮件用得体的英文发给客户”。

| 形态 | 用户成本 | AI 适配度 | 备注 |
|---|---|---|---|
| 聊天机器人，粘贴邮件并输入“帮我翻译成英文” | 高（打字说明、等待整段） | 低效 | Demo 最快，体验最差 |
| 选中文本 → 一键改写 → 直接替换 | 低 | 高 | 把输出直接写进用户流程 |
| 写邮件时实时建议（自动补全） | 最低 | 中 | 片段生成、Tab 接受 |
| 发送前检查语气并给出修改建议 | 低 | 高 | “建议—确认”模式 |

四种形态用同一个模型，但产品价值天差地别——**差别在于设计，不在模型。** 设计师的价值就是把第一种改成第三种。

**③ 现成的 AI 设计准则**：微软的 HAX（人机交互指南，Amershi 等，2019）提出了 18 条准则，例如“让系统能力清晰可见”“支持高效的纠正与忽略”“拿不准时缩小服务范围”“展示与上下文相关的信息”；Google 的 PAIR 指南也有类似内容。它们可直接用来评审 LLM 产品原型。

**④ 打破范式的例子**：GitHub Copilot 不是“聊天”，而是 IDE 内联补全；Cursor 等后来又把“对话”和“Tab 接受”结合；Midjourney 用“四选一 + 变体”而非“文字描述精修”。这些都是设计先于技术形态的例子。

### 为人在回路（HITL）设计 UX

**【原文】** 获得高质量标注的一条路，是把人在回路**集成进用户体验**：让用户方便地反馈与纠正，既能改善当下的输出，又能收集宝贵的数据。

设想一个电商平台，用户上传并给商品分类，有几种 UX 设计：
1. 用户手动选择类目；LLM 定期检查新商品，在后端纠正错误分类；
2. 用户完全不选；LLM 在后端定期分类（可能有错）；
3. LLM **实时建议**一个类目，用户验证并按需修改。

三者都用到了 LLM，但 UX 截然不同。第一种把负担先放在用户身上，LLM 只做事后检查；第二种用户零努力，但没有透明度和控制权；**第三种取得了恰当的平衡**：LLM 先给建议，降低了用户的认知负担——他们不需要学会我们的分类体系；同时用户可以审阅和修改，**对商品如何分类拥有最终决定权**。额外好处是，第三种天然形成了模型改进的反馈闭环：好的建议被接受（正样本），差的被修改（负样本 + 紧接的正样本）。

这种“建议 → 用户验证 → 收集数据”的模式见于：
- **编程助手**：接受建议（强正）、接受并微调（正）、忽略（负）；
- **Midjourney**：放大并下载（强正）、做变体（正）、重新生成一组（负）；
- **聊天机器人**：点赞（正）、点踩（负）、重新生成（强负）。

反馈分**显式**与**隐式**：显式是产品主动请求后用户给出的；隐式是从用户交互中学到的、无需用户刻意提供。编程助手和 Midjourney 是隐式反馈，点赞点踩是显式。**如果 UX 设计得好，可以收集到大量隐式反馈。**

**【扩展】**

**① 这段的核心洞察是：UX 不只是界面，它是数据采集渠道。** 产品设计与第 1 章的“评估”、本章的“数据”连成了一条线：好的 UX → 高质量标注 → 更好的评测与微调 → 更好的模型 → 更好的 UX。这就是所谓**数据飞轮**，而它的起点是“让用户顺手就能纠正”。

**② 隐式反馈并不干净——要小心三种偏差**

| 偏差 | 表现 | 缓解 |
|---|---|---|
| **可验证性偏差** | 用户只接受自己能看懂的建议；看不懂的（比如复杂代码）既不接受也不拒绝 | 别把“忽略”一律当负样本；结合停留时长、后续是否回滚 |
| **选择性偏差** | 用户只对特别差或特别好的才点踩/点赞，中间地带沉默 | 别用点赞率估计整体准确率；它只反映分布尾部 |
| **习惯性接受** | 审批界面上“一路点确认”，反馈成了橡皮图章 | 只在模型不确定或高风险时请求确认；监测“接受率”是否高得不正常 |

**③ 信号强度分层**：把反馈映射成强弱不同的标签，例如“原样接受 = +1、编辑后接受 = +0.5、拒绝/重新生成 = −1、忽略 = 未知（不计入）”。这样弱信号也能用，但不会被当成强信号。

**④ HITL 的三种介入时机**

| 模式 | 说明 | 适用 | 代价 |
|---|---|---|---|
| **用前审批** | 输出先给人看，确认后才生效 | 高风险、不可逆操作（发邮件、下单、写库） | 每次都付人工成本 |
| **用后修正** | 先生效，用户可编辑/撤销 | 中低风险、可逆 | 依赖用户发现问题 |
| **抽样审查** | 绝大多数自动通过，抽一部分人工复核 | 低风险、高频率 | 发现问题有滞后 |

选择依据是“**错误代价 × 发生频率**”：高代价 + 低频 → 用前审批；低代价 + 高频 → 自动 + 抽样；中间地带 → 用后修正 + 易于撤销。

**⑤ 成书后的新形态**：这个模式已从“建议一个类目”扩展到 Agent——Agent 先给出**计划**或**代码 diff**，人审阅后批准执行（现代编码 Agent 的“审查 diff”、Agent 的“计划确认”）。本质没变：**先看后做，最终决定权在人。**

**⑥ 隐私提醒**：隐式反馈日志记录了用户行为，属于用户数据，受留存与合规约束；而且不要把“用户接受”直接当作训练数据——先经过清洗与抽检，否则会把“用户的迁就”学进去。

### 无情地排优先级

**【原文】** 把 Demo 推向生产时要考虑这些需求：
- **可靠性**：99.9% 正常运行时间，遵守结构化输出；
- **无害性**：不生成冒犯性、NSFW 或其他有害内容；
- **事实一致性**：忠于提供的上下文，不编造；
- **有用性**：与用户的需求和请求相关；
- **可扩展性**：延迟 SLA、支持的吞吐量；
- **成本**：预算不是无限的；
- **以及更多**：安全、隐私、公平性、GDPR、DMA 等。

如果同时应对所有需求，永远发不了版。所以要排优先级，**无情地**。这意味着明确什么是不可妥协的（如可靠性、无害性）——没有它们产品无法运作或不具可行性。关键在于找出“**最小可爱好产品**”。必须接受第一版不会完美，**先上线再迭代**。

**【扩展】**

**① 把需求分成“门槛”与“预算”两类，排优先级就容易了**：

| 类别 | 含义 | 例子 | 管理方式 |
|---|---|---|---|
| **门槛**（gate） | 不达标就不能上线；不随时间“换” | 无害性、合规、数据不出域 | 二值判断，上线前必须全过 |
| **预算**（budget） | 有定量目标，可以权衡、可以欠债 | 可用性、延迟、成本、事实一致性 | 设 SLO 与“错误预算”，超标再修 |
| **增益**（nice-to-have） | 影响体验但非必需 | 有用性的精细打磨、语气风格 | 排进后续迭代 |

书中说“可靠性、无害性不可妥协”，是门槛；延迟、成本是典型的预算；有用性多数时候是增益，但对某些产品（如搜索）会成为门槛。

**② 风险矩阵——决定哪一项该是门槛**

| | 错误可逆 | 错误不可逆 |
|---|---|---|
| **错误代价高** | 用后修正 + 易撤销（如草稿生成） | 用前审批 + 高门槛（如转账、医疗建议） |
| **错误代价低** | 自动 + 抽样审查（如分类、标签） | 自动 + 监控（如一次性推荐） |

右上角格子里的需求，几乎都会被提为门槛；左下角的则多为增益。**同一个技术，在不同象限的“最低标准”完全不同。**

**③ “最小可爱好产品”与“最小可行产品”的区别**：前者在“能跑”之外还要求用户**愿意用**——否则没有反馈闭环，“上线再迭代”的“迭代”就无从谈起。对 LLM 产品，“可爱”往往意味着：响应快（流式输出）、错了能改（HITL）、说不知道时不令人讨厌。

**④ “先上线再迭代”的边界**：这句话在内部工具、低风险场景里完全正确；在受监管、高风险场景里，上线前必须先过门槛，“迭代”只能在增益层面进行。作者在下一小节正是要说明这一点。

### 根据用例校准风险容忍度

**【原文】** 决定用什么模型、做多严格的审查时，要考虑用例和受众。对提供医疗或金融建议的面向客户的聊天机器人，安全与准确性的标准要非常高——错误或坏输出会造成真实伤害并侵蚀信任。但对不那么关键的应用，如推荐系统，或面向内部的应用如内容分类、摘要，**过于严格的要求只会拖慢进度而不增加多少价值**。

这与 a16z 的一份报告一致：很多公司做**内部** LLM 应用比**外部**的更快。通过用 AI 做内部生产力实验，组织可以在更可控的环境里开始获取价值、学习管理风险；随着信心增加，再扩展到面向客户的场景。

**【扩展】**

**① 一条渐进的阶梯（我的总结）**

| 级别 | 形态 | 错误由谁兜底 | 典型门槛 |
|---|---|---|---|
| 1 | 内部工具，个人使用 | 使用者自己 | 无害性、数据不出域 |
| 2 | 内部工具，多人流程的一环 | 下一环节的人 | + 可靠性、格式合规、可追溯 |
| 3 | 面向客户，人在回路 | 员工审核后才到客户 | + 事实一致性、审计日志 |
| 4 | 面向客户，自动执行 | 系统 | + 高标准安全与合规、回滚、监控告警 |

每升一级，门槛增加、评测集扩大、上线审批更严。**先从低级别积累评测集与运营经验，再升级。**

**② 成书后，这部分从“建议”变成了“法规”**：欧盟《人工智能法案》于 2024 年生效，按风险分级——不可接受、高风险、有限风险、最小风险——高风险系统的要求包括风险管理、数据治理、技术文档、日志、**人工监督**与准确性/鲁棒性。这意味着在某些用例里，“人在回路”与“可追溯”不再是产品选择，而是法律义务（2026 年 7 月生效的 Digital Omnibus 把 Annex III 高风险义务的适用日推迟到了 2027 年 12 月 2 日）。国内也有《生成式人工智能服务管理暂行办法》（2023 年施行），以及生成合成内容标识的相关规定（2025 年 9 月施行）。做合规相关决策请以最新法规原文为准。

**③ “内部先行”仍然成立，但有两个新变化**：
- 内部工具也会触达敏感数据——**“内部”不等于“无风险”**，数据分级与权限隔离仍然是门槛；
- 2025 年之后 Agent 能“动手”（调工具、改数据）了，内部 Agent 的风险等级比内部聊天机器人高得多，“级别 2”要按“是否能执行操作”再细分。

**④ 数据侧的硬门槛**：数据是否可以发给第三方 API、是否用于供应商训练（零留存协议）、数据驻留、脱敏——在很多组织里，这几项决定了“能不能用前沿模型”，进而反过来影响模型选型（见 2.4）。**先回答数据能不能出去，再比较模型好坏。**

## 团队与角色（Team and Roles）

**【原文】** 没有哪个岗位职责是容易定义的，但为这个新领域写岗位说明比别的更难。作者不做岗位标题的维恩图，也不提供岗位说明模板；但承认一个新角色——**AI 工程师**——的存在，并讨论团队其他成员及职责如何分配。

### 关注流程，而非工具

**【原文】** 面对新范式时，软件工程师倾向于选择工具。结果我们忽略了工具本要解决的问题与流程，承担了**偶然复杂度**（accidental complexity），损害团队长期生产力。

例如，有文章讨论某些工具能自动为 LLM 写 Prompt，并（作者认为说得对）指出：不先理解解决问题的方法论与流程就用这些工具的工程师，最终会背上不必要的技术债。

此外，工具往往**规格不清**。LLM 评测工具正在形成产业，提供“开箱即用的 LLM 评测”——针对毒性、简洁、语气等的通用评估器。作者见过很多团队采用这些工具，却**没有批判性地思考自己领域的具体失败模式**。与之对照的是 **EvalGen**：它通过让用户深度参与每一步——从定义标准、标注数据到检查评测——来教用户**创建领域专属评测的流程**：

1. 定义领域专属的测试（从 Prompt 自动引导生成），形式为代码断言或 LLM-as-Judge；
2. 让测试与人类判断对齐，以便用户检查测试是否捕捉到了指定的标准；
3. 随系统（Prompt 等）变化，迭代测试。

EvalGen 给开发者的是评测构建过程的**心智模型**，而不绑定到某个工具。作者发现，给了 AI 工程师这些背景之后，他们常常会选择更精简的工具，或者自己构建。

LLM 的组件太多，无法在此穷举。但重要的是：AI 工程师在采用工具之前，先去理解流程。

**【扩展】**

**① “偶然复杂度” vs “本质复杂度”**：这是 Fred Brooks 在 1986 年的文章《没有银弹》里提出的区分——本质复杂度是问题固有的，偶然复杂度是我们选择的工具与方法带来的。LLM 应用的本质复杂度在于：定义“好输出”（评测）、管理数据分布、设计人在回路。工具解决不了这些，它只能加速你已经想清楚的事。**在没想清楚之前用工具，只是把混乱自动化了。**

**② 为什么“开箱即用的评测”是个陷阱**：通用评估器（“是否有毒”“是否简洁”）衡量的是所有任务共有的、最不重要的维度。真正决定你产品质量的是**领域特有的失败模式**——“药名剂量抽错”“金额单位错”“把‘不适用’编成了具体日期”。这些只能来自看数据、来自领域专家。**评测是领域知识的编码，买不来。**

**③ 什么时候该用工具（我的判断）**

| 类型 | 例子 | 建议 |
|---|---|---|
| 商品化基础设施 | 调用网关、追踪、日志、实验跟踪、标注平台 | 买/用现成的 |
| 通用能力 | 通用护栏（PII、毒性）、嵌入模型 | 用现成的，但要验证在自己数据上的表现 |
| **领域知识的编码** | **评测集与评分标准、错误分类、Prompt** | **自己建，别外包给“开箱即用”** |

**④ 对 Agent 框架同样适用**：2024～2026 年 Agent 框架层出不穷，迭代极快。先理解“你的 Agent 需要什么流程”（状态、工具、验证点、人在哪里介入），再选框架；否则框架的抽象会变成枷锁。业界的经验之一是：**成熟的团队往往用的是很薄的框架，因为流程长在自己脑子里。**

### 永远在实验

**【原文】** ML 产品与实验深度交织。不只是 A/B、随机对照试验那种，还包括频繁地修改系统里**尽可能小的组件**并做离线评估。**大家对评测如此热衷，其实不是为了可信度与信心——而是为了让实验成为可能！** 评测越好，实验迭代越快，也就越快收敛到系统的最佳版本。

因为实验现在很便宜，对同一问题尝试不同方法很常见——收集数据和训练模型的高成本被最小化了，Prompt 工程的成本几乎只是人的时间。**让团队每个人学会 Prompt 工程基础**，鼓励所有人实验，带来组织内多元的想法。

此外，不要只为**探索**而实验，也要用它来**利用**（exploit）！新任务有了一个可行版本？让团队里另一个人用不同方法做一遍。试试更快的另一种方式。研究思维链、few-shot 等技巧提升质量。**别让工具拖累实验，如果拖累了，重建它或买一个更好的。**

最后，在产品/项目规划时，**为构建评测和多次实验预留时间**。像工程产品一样写产品规格，但加上清晰的评测标准。做路线图时不要低估实验时间——预期要做多轮开发与评测，才能获得上生产的“绿灯”。

**【扩展】**

**① “评测是为了实验”是一个很锐利的视角**。它把评测从“质量保证”的防御性活动，变成“迭代速度”的进攻性活动。可以用一个链式不等式表达：

> 更好的评测 → 更快的实验 → 更多的尝试 → 更快收敛到好系统

所以**迭代周期时间**（从一个想法到得出“行/不行”结论的时间）是 LLM 团队最重要的健康指标之一。去测量它，然后缩短它。

**② 探索与利用**：这组词来自多臂老虎机/强化学习。探索 = 尝试不同的方法（换流程、换模型、换拆分方式）；利用 = 在已可行的方法上持续改进（加示例、加 CoT、换更便宜的模型）。健康的团队两者都做，常见错误是**只利用不探索**——找到一个 70 分的方案后不断打磨，而没试试另一种可能是 90 分的方案。书中“让另一个人用不同方法做一遍”就是制度化的探索。

**③ 离线实验 vs. 在线 A/B**

| | 离线评测 | 在线 A/B |
|---|---|---|
| 速度 | 快（分钟～小时） | 慢（数天～数周） |
| 噪声 | 低，可重复 | 高，需要流量与统计功效 |
| 回答的问题 | “输出质量变了吗” | “用户行为/业务指标变了吗” |
| 盲点 | 评测集偏差；不等于用户满意 | 只告诉你 A/B 不同，不告诉你为什么 |

实践顺序：离线筛掉明显差的 → 小流量 A/B → 看懂差异 → 沉淀回评测集。

**④ 实验纪律（我的补充）**：一次只改一个变量；固定模型版本与随机种子（减少噪声）；每次实验记录完整的配置与结果（实验跟踪工具）；设定“最小可检测效应”，样本量不够时别下结论；**每个失败的实验都要“读样本”**——知道为什么失败，比知道分数重要。

**⑤ “预留时间”的量化**：业界经验是，从 Demo 到可上线的 LLM 功能，通常要经历多轮（常见说法是 3～10 轮）“开发—评测”循环；排期时如果只给一轮，等于没有给实验留时间。在 PRD 里写明评测标准，会让产品与工程在开工前就对齐“什么叫好”。

### 赋能每个人使用新的 AI 技术

**【原文】** 随着生成式 AI 的采用率增加，我们希望**整个团队**——不只是专家——理解并有信心使用新技术。没有比“用”更好的方式来培养对 LLM 工作方式的直觉（延迟、失败模式、UX）。LLM 相对平易：不需要会写代码就能改进流水线表现，每个人都可以从 Prompt 工程和评测开始贡献。

一大部分是**教育**。可以从 Prompt 工程基础开始——n-shot、CoT 如何把模型引向期望的输出。有相关知识的人还可以讲更技术的部分，比如 LLM 的**自回归**本质：输入 token 并行处理，输出 token 依次生成。因此，**延迟更多取决于输出长度而不是输入长度**——这是设计 UX 和设定性能预期时的关键考量。

还可以更进一步，提供动手实验与探索的机会。比如黑客松？让整个团队花几天捣鼓“探索性”的项目看起来昂贵，但结果可能令人惊讶。作者知道一个团队通过黑客松，把三年的路线图在一年内几乎完成；另一个团队的黑客松产生了范式转变的、多亏了 LLM 才成为可能的 UX，已被列为当年及以后的重点。

**【扩展】**

**① 把“延迟取决于输出长度”写成一个公式**

```
总延迟 ≈ 首 token 时间(TTFT) + 输出 token 数 × 每 token 时间(ITL)

TTFT  ∝ 输入长度（prefill 阶段，并行计算）
ITL   与输出内容相关，基本与输入长度无关（decode 阶段，逐个生成）
```

数字感受：输入 1 万 token 的 prefill 可能只要几百毫秒到一两秒；而输出 1000 token、每 token 50 毫秒就是 50 秒。**所以长输入便宜，长输出贵。**

**② 对 UX 的直接含义**

| 策略 | 做法 |
|---|---|
| 流式输出 | 用户感知等待大幅下降，即使总时长不变 |
| 骨架屏 / 分段展示 | 先给结构，再填内容 |
| 限制输出长度 | 让模型“先给 3 条要点”而非“写一篇长文” |
| 把长生成移到后台 | 先返回任务 ID，完成后通知 |
| 预填 + 短确认 | 让模型少生成，多由用户确认 |

**③ 成书后的变化**：前缀缓存与更快的 prefill 让 TTFT 显著下降；但**推理模型引入了“思考 token”**——模型在给出答案前生成大量（用户不可见或折叠的）推理内容，这部分同样按输出 token 计费、同样贡献延迟。所以“延迟 ∝ 输出长度”在今天更加成立，只是“输出”里多了一截看不见的部分。UX 上要给用户明确的“正在思考”的反馈，并允许在不需要深度推理的任务上关闭推理。

**④ “赋能每个人”的落地方式（我的补充）**：内部 Prompt 库与案例分享；定期的“看数据”开放日（非工程师也参与错误分析——他们往往最懂业务）；办公时间（懂技术的人答疑）；黑客松——但要设主题和评审标准，产出要有去处（进路线图或归档）。

**⑤ 谁最该被赋能？领域专家。** 评测标准、失败模式、好的示例，最终都来自最懂业务的人。让他们会用 Prompt，就能直接参与评测集建设——这是比“让每个人都去搭 Agent”更高杠杆的事。

### 别掉进“只要有 AI 工程师就够了”的陷阱

**【原文】** 新岗位名称出现时，初期总倾向于夸大其能力范围，随后往往迎来痛苦的修正。过去十年值得注意的例子：
- **数据科学家**：“比任何软件工程师更懂统计、比任何统计学家更会软件工程的人”；
- **机器学习工程师（MLE）**：以软件工程为中心视角看待机器学习。

起初很多人以为光有数据科学家就能做数据驱动的项目，后来才发现他们必须与软件工程师、数据工程师协作才能开发和部署数据产品。

这种误解在 **AI 工程师**这个新角色上重演了：有些团队相信 AI 工程师就是全部。实际上，构建 ML/AI 产品需要广泛的专门角色。**作者们为十几家公司提供过 AI 产品咨询，一致观察到它们掉进“只要有 AI 工程师就够了”的陷阱。** 结果是，产品常常难以超越 Demo，因为公司忽视了构建产品的关键方面。

例如，**评估与度量**是把产品扩展到超出“vibe check”的关键，而有效评估所需的能力与传统上 MLE 的优势一致——**只有 AI 工程师的团队很可能缺乏这些技能**。作者之一 Hamel Husain 在近期关于检测数据漂移与设计领域专属评测的工作中，阐明了这些技能的重要性。

作者给出 AI 产品历程中**所需角色的类型与时机**的大致进程：

1. **先专注把产品做出来。** 可以有 AI 工程师，但不是必须。AI 工程师在快速原型与迭代产品（UX、管道连接等）上很有价值。
2. **接着，通过给系统埋点、收集数据来建立正确的基础。** 取决于数据的类型与规模，可能需要平台工程师和/或数据工程师。还必须有查询与分析这些数据以调试问题的系统。
3. **最后，才会想优化 AI 系统。** 这不一定要训练模型，基础工作包括设计指标、构建评测系统、跑实验、优化 RAG 检索、调试随机系统等。**MLE 擅长这些**（AI 工程师也能学会）。在完成前置步骤之前招 MLE 通常没有意义。

除此之外，**任何阶段都需要领域专家**：小公司里最好由创始团队担任，大公司里产品经理可以扮演这个角色。**了解角色的进程与时机至关重要**——在错误的时机招人（如太早招 MLE），或者以错误的顺序构建，是对时间和资金的浪费，并造成人员流失。此外，在阶段 1–2 定期咨询 MLE（但不必全职）能帮助公司建立正确的基础。

**【扩展】**

**① 各角色到底管什么（我的梳理）**

| 角色 | 核心职责 | 在 LLM 应用里的具体体现 | 常见误解 |
|---|---|---|---|
| AI 工程师 | 用 API 快速把模型能力做成产品 | Prompt、流程编排、工具调用、UX 打通 | 以为评测也可以“顺手”做 |
| ML 工程师 | 让模型系统可度量、可优化、可维护 | 指标设计、评测体系、实验方法、调试随机系统 | 以为“不训练模型就不需要” |
| 数据 / 平台工程师 | 让数据可得、可查、可追溯 | 日志、埋点、数据管道、追踪、特征/索引 | 以为“上线后再补” |
| 产品经理 | 定义任务、优先级、风险门槛 | 待完成的任务、验收标准、合规边界 | 以为 Demo 成功 = 产品成功 |
| 设计师 | 把需求重新表述成可解的形态 | 交互模式、HITL、反馈采集 | 以为只是“美化界面” |
| **领域专家** | 知道什么是“对” | 评测标准、失败模式、示例 | 以为“看完需求就可以退场” |

**② 这张表暴露了“AI 工程师就够了”为什么错**：AI 工程师擅长把东西**做出来**，但“做对”（评测）、“做稳”（数据与平台）、“做该做的”（产品与领域）分别需要别的能力。Demo 做得越快，这个缺口越容易被掩盖——直到上线。

**③ 为什么“太早招 MLE 是浪费”**：MLE 的杠杆在于优化——而优化需要先有东西可优化（产品）和能度量的东西（数据）。没有埋点就没有数据，没有数据评测就是空中楼阁，这时 MLE 再强也无事可做。**但作者的建议是“定期咨询”**——花很少的钱，在阶段 1～2 就把埋点与评测的地基打对，避免返工。

**④ 我认为书里有一处需要修正的张力**：第 1 章说评测是 LLM 应用最重要的事，本节又说“太早招 MLE 没意义”。两者可以调和，但要讲清楚：**第一天就需要的是看样本、做错误分析的能力，不是一套自动化评测系统；评测的专岗可以晚一点再招。** 换句话说，阶段 1 的团队里必须有人懂评测（哪怕是 AI 工程师自己学会，或外部顾问），只是不必为此专门配一个全职 MLE。同理，“埋点”不该等到阶段 2——如果阶段 1 不埋点，阶段 2 就没有数据可收。**我的建议是把顺序改成“产品与埋点同步起步”。**

**⑤ “hidden technical debt”——ML 系统的技术债长得不一样**：Sculley 等人 2015 年的经典论文指出，ML 系统最大的技术债不在模型代码，而在**胶水代码、管道丛林、配置、未声明的消费者、外围组件**。LLM 应用完全继承了这些债，而且多了一项：**对不受控的外部依赖（模型供应商）的债**（见 2.3）。多角色协作的意义正在于此——这些债分布在系统的不同角落，没有人能独自看见。

**⑥ 成书之后：“AI 工程师”本身在分化**（业界观察，尚非定论）：随着 LLM 功能触及检索、评测、Agent、推理成本与安全，一个“AI 工程师”很难同时精通；业界讨论中出现了更细的分工——评测、上下文工程、LLMOps/平台、AI 安全等。同时，AI 编码助手让小团队能交付更多，所以“更少的人 + 更全的工具”也成为可能。两种趋势并存：**头衔在分化，但对每个人的“流程理解”（4.1）的要求没有降低。**

**⑦ 关于“派驻式工程师”（FDE）**：模型供应商与 AI 公司越来越倾向于把工程师派到客户现场共建应用。这对加速落地很有帮助，但要注意别把系统绑死在单一供应商上——模型是一个“带退役日期的依赖”（2.3）。

## 书里说得不够或可以商榷的

成书两年多以后，各节的变化已经写在上面的【扩展】里，逐条的现状核对放在[第四篇](/posts/llm-year-04/)。这里只记本章书里没讲到、说得不够，或者我觉得可以商榷的地方：

1. **安全几乎是空白**。整章只在“以及更多”里提了一句安全与隐私。但对 LLM 应用来说，提示注入、数据泄露、越狱、工具滥用是运营阶段最常见的风险，应当在“门槛”里占一席之地。
2. **成本与“FinOps”没有展开**。成本只作为一项需求被列出；而模型选型、路由、缓存、预算告警已足够单独成一节（第 1 章讲了缓存，本章讲了小模型，但没有串起来）。
3. **事故响应缺失**。模型供应商故障、速率限制、内容过滤误拦、输出格式漂移——需要有预案、有值班手册、有演练。
4. **“实验现在很便宜”说得过于轻巧**。改 Prompt 便宜，但**评测贵**——评测集的建设与维护、人工标注、LLM-as-Judge 的校准，才是迭代成本的瓶颈。更准确的说法是：实验的边际成本在下降，固定成本（评测）没变。
5. **“先上线再迭代”需要限定条件**。内部、低风险场景适用；面向客户或受监管场景，门槛要先过。
6. **“MLE 晚点招”与“评测最重要”之间的张力**没有被正面处理（见 4.4 ④）。
7. **对非确定性、采样方差下的统计决策**（需要多少样本、多大的提升才算显著）没有讨论，导致“跑两次看结果”式的实验很常见。

## 贯穿全章的底层思想（提炼）

读完第 2 章，我把散落的建议归纳为**七条原则**：

1. **去看数据，别只看指标**。指标告诉你“变了”，样本告诉你“为什么”。每天看，把它写进值班职责。
2. **把模型当作带退役日期的外部依赖**。固定版本、影子验证、灰度回滚、弃用日历——像对待一个你控制不了的第三方服务那样对待它。
3. **能小则小，按步骤选型**。前沿模型用来验证可行性，小模型 + 流程工程用来规模化；没有评测集就不要谈选型。
4. **UX 是数据渠道**。建议 → 用户验证 → 数据 → 更好的模型。人在回路既是安全阀，也是标注工厂。
5. **需求分层，按风险定标准**。门槛（不可妥协）、预算（可权衡）、增益（可迭代）；错误代价与可逆性决定哪一项该是门槛。
6. **流程先于工具，评测先于优化**。工具放大你已有的理解；评测缩短你的迭代周期。
7. **角色随阶段演进，领域专家贯穿始终**。先把产品做出来，同时打好埋点，再谈优化；别指望一个角色包打天下。

与第 1 章的连接：第 1 章的原则是“**用确定性包裹概率性**”，第 2 章的原则是“**用流程与产品包裹不确定性**”。前者是技术，后者是组织——两者缺一，Demo 都变不成产品。

## 落地检查清单

**数据**
- [ ] 是否记录了完整的输入输出（含拼接后的 Prompt、模型版本、检索结果、工具调用）？
- [ ] 是否每天有人抽样看样本？是否已纳入值班职责？
- [ ] 是否监测结构性偏差（长度、格式合规率）与语义漂移（嵌入聚类）？
- [ ] 留出集是否反映最近的真实交互（含错别字、口语、边界情况）？
- [ ] 评测是否对同一输入多次运行并统计方差？
- [ ] 发现新失败模式后，是否在 24 小时内变成一条断言？

**模型**
- [ ] 输出是否走结构化 Schema？是否有第二层业务规则校验？
- [ ] 生产是否只用带版本号的模型 ID？模型 ID 是否只存在一处配置？
- [ ] 是否有基于线上样本的黄金集？每次模型/Prompt 变更是否自动跑回归？
- [ ] 是否有影子流水线？是否有灰度发布与一键回滚？
- [ ] 是否维护“模型清单 + 退役日期 + 负责人”？
- [ ] 是否验证过“任务用小模型是否够用”？是否按步骤而非按应用选型？

**产品**
- [ ] 设计师是否在定义问题（而非仅美化界面）时就参与？
- [ ] 是否用“待完成的任务”审视过形态：聊天、补全，还是别的？
- [ ] 用户是否能方便地纠正输出？纠正是否被记录为标注？
- [ ] 是否区分了门槛、预算、增益？门槛是否全部达标？
- [ ] 是否画过“错误代价 × 可逆性”矩阵，并据此决定 HITL 介入时机？
- [ ] 隐式反馈是否处理了可验证性偏差与习惯性接受？

**团队**
- [ ] 采用工具前，是否先弄清了它要解决的流程？评测标准是否自建？
- [ ] 是否测量了“迭代周期时间”？排期是否预留了多轮“开发—评测”？
- [ ] 团队里每个人是否学过 Prompt 基础？领域专家是否参与了评测集建设？
- [ ] 是否明确知道当前处于哪个阶段（做产品 / 打基础 / 优化），并与人员配置匹配？
- [ ] 埋点是否从第一天就开始（而非等到第二阶段）？
- [ ] 是否有外部 MLE 顾问在早期阶段定期把关？
