前两章分别回答了“怎么做”（战术：具体动作）和“用什么流程支撑做”（运营：更高层的流程）。第 3 章回答的是**这些目标从哪里来**——也就是战略：战术和运营背后“做什么”与“为什么”。

作者给出了几条旗帜鲜明的口号，例如“**PMF（产品—市场匹配）之前不买 GPU**”、“**关注系统，而不是模型**”，用来帮团队决定稀缺资源投向哪里。全章围绕六个问题：

| 问题 | 一句话答案（书中） |
|---|---|
| **自建还是购买** | 何时该自己训模型、何时用现成 API？——“看情况”，作者说明看哪些情况 |
| **迭代到卓越** | 如何建立超越“用最新模型”的持久优势？——在模型周围建健壮的系统，做令人难忘、有粘性的体验 |
| **以人为中心的 AI** | 如何把 LLM 融入人类工作流以最大化生产力与幸福感？——增强人，而不是取代人 |
| **如何起步** | 什么是最基本的步骤？——Prompt 工程、评测、数据收集 |
| **低成本认知的未来** | 成本下降和能力提升会怎样塑造应用？——用历史趋势做推算 |
| **从 Demo 到产品** | 中间隔着什么？——严谨的工程、测试与打磨 |

作者的收束语值得记住：成功的产品需要深思熟虑的规划与艰难的取舍，而不是无休止的原型，也不是追逐最新的模型和潮流。开篇还开了一句玩笑——“让我们一步步思考”（think step by step），把第 1 章的 CoT 用在了章节组织上。

## PMF 之前不要买 GPU（No GPUs Before PMF）

**【原文】** 要做出色的产品，它不能只是别人 API 外面的一层薄包装。但反方向的错误代价更高：过去一年大量风险资本（书中提到一笔“高得刺眼的”巨额融资）投向了训练和定制模型，却没有清晰的产品愿景或目标市场。本节解释为什么一上来就自己训模型是个错误，并讨论自托管的定位。

### 从零训练（几乎）从不划算

**【原文】** 对多数组织来说，从零预训练一个 LLM 是不切实际的，会让人从做产品这件事上分心。开发和维护 ML 基础设施需要大量资源：收集数据、训练与评估模型、部署。如果你还在验证 PMF，这些投入会从核心产品上抽走资源。**即便你有算力、数据和技术，预训练出来的模型也可能在几个月内过时。**

例子是 **BloombergGPT**，一个专为金融任务训练的 LLM：在 **3630 亿 token** 上预训练，需要 **9 名全职员工**（4 名 AI 工程师、5 名 ML 产品与研究）的“英雄式”努力。尽管如此，**一年之内它就在这些金融任务上被 gpt-3.5-turbo 和 gpt-4 超越**。

这个故事说明：对多数实际应用来说，即使用领域数据从零预训练，也不是资源的最优用法。更好的做法是**针对自身需求微调最强的开源模型**。

当然有例外：**Replit 的代码模型**专为代码生成与理解训练，预训练使其超过了 CodeLlama-7b 等更大的模型。但随着更强的模型发布，**维持这种优势需要持续投入**。

**【扩展】**

**① BloombergGPT 的细节与后续**：该模型有 500 亿参数，论文发表于 2023 年（[Wu et al., 2023](https://arxiv.org/abs/2303.17564)）。随后有研究在金融 NLP 任务上对比 BloombergGPT 与 ChatGPT/GPT-4，发现通用模型在多数任务上持平或更好（[Li et al., 2023](https://arxiv.org/abs/2305.05862)）。“一年内被通用模型超越”这个时间线是真实发生过的，而不是假设。

**② 为什么“领域预训练”常常输给通用模型？** 三个原因：
- **规模与数据质量**：公开网页数据里的金融文本（财报、研报、新闻）远多于一家公司的私有语料；通用模型“顺便”学会了金融。
- **能力迁移**：推理、指令遵循这些通用能力是跨领域迁移的，小语料预训练补不上。
- **追赶成本**：每次基座进步，你都要重训一遍。

**③ 什么时候从零训练/继续预训练仍然合理？（我的判断）**

| 条件 | 说明 |
|---|---|
| 你就是要卖模型 | 模型本身是产品（模型实验室、需要差异化模型能力的产品） |
| 数据不在公开网络上，且量极大 | 例如独有的行业日志、专有传感器数据——并且通用模型在你的评测上确实不行 |
| 有强约束的延迟/成本/离线要求 | 边缘设备、隐私要求高到不能用 API |
| 有长期投入的预算与团队 | 不是一次性的，而是每个基座版本都要重做 |

四条缺一，就先考虑“微调最强开源模型”这条路。

**④ Replit 例子说明的不是“预训练可行”，而是“预训练是一次性领先”**：它的优势来自率先在代码上投入；当 CodeLlama、StarCoder、DeepSeek-Coder 等陆续出现，领先窗口就被抹平了。**除非你有持续投入的机制，否则一次性的模型领先不构成长期优势。**

### 没证明必要之前不要微调

**【原文】** 对多数组织来说，微调更多是被 **FOMO**（怕错过）驱动的，而不是清晰的战略思考。组织过早投入微调，想反驳“你只是个套壳”的指责。实际上，**微调是重型机械**，只有在收集了大量示例、足以让你确信其他方法不够用之后，才该拿出来用。

一年前很多团队兴奋地说要微调；**很少有人找到 PMF，多数人后悔这个决定。** 如果要微调，你最好非常确信：随着基座模型进步，**你准备好一遍又一遍地重做**（见 2.1 与 2.3）。

什么时候微调才真的对？如果用例需要的数据**不在现有模型训练所用的公开网络规模数据集里**，并且你**已经做了 MVP，证明现有模型不够用**。但要小心：**如果连模型构建者都拿不到好的训练数据，你的数据是从哪来的？**

最后记住：**LLM 应用不是科学展览项目**，投入应与它对业务战略目标和竞争优势的贡献相称。

**【扩展】**

**① “重型机械”重在哪？** 不在训练本身（如今 LoRA/QLoRA 让训练成本很低），而在这四件事：
1. 收集与标注高质量数据；
2. 维护一套能判断“微调是否更好”的评测；
3. 基座每次更新就重做一遍；
4. 自托管的运维（如果为了微调而自托管）。

**② 该与不该微调的信号（我的清单）**

| 不该微调的信号 | 该微调的信号 |
|---|---|
| 目的是“听起来不像套壳” | Prompt 和 RAG 都试过，评测显示确有瓶颈 |
| 还没有评测集 | 有几百到几千条高质量、领域专属的样本 |
| 想让模型“知道”新事实（→ 该用 RAG） | 需要特定的输出格式/DSL/风格，Prompt 难以稳定 |
| 任务定义还在变 | 任务稳定、调用量大，延迟/成本压力真实存在 |
| 数据是“模型也能从网上学到的” | 数据确实不公开，且模型在你的评测上明显不足 |

**③ 成书后的变化**：训练后方法在 2024–2026 年变得更加便宜（参数高效微调、偏好优化等），“重做一遍”的单次成本下降；但**评测与数据管线才是持续的负担**，这一点没变。同时，“用小模型微调替代大模型 API”成为一种成本策略（见第 2 章 2.4），这与本章“微调要有战略理由”并不矛盾——那里的理由是成本与延迟，是明确的。

**④ 一句提醒**：作者的“多数人后悔”来自咨询经验的观察，不是统计数据；但它与“重型机械”的判断一致，值得当作先验。

### 从推理 API 起步，但不要怕自托管

**【原文】** 有了 LLM API，创业公司不必从零训练就能集成语言建模能力。Anthropic、OpenAI 等供应商的通用 API，几行代码就能给产品“撒上智能”。用这些服务可以减少投入，把精力放在为用户创造价值上——更快验证想法、更快迭代到 PMF。

但就像数据库一样，**托管服务并不适合所有用例**，尤其当规模与要求提高时。**自托管可能是在不把机密/隐私数据传出网络的前提下使用模型的唯一方式**——医疗、金融等受监管行业，或合同、保密要求都需要。此外，自托管绕开了推理供应商的限制：**速率限制、模型弃用、使用限制**。它还给你对模型的完全控制，更容易在它周围构建差异化的高质量系统。最后，自托管（尤其是微调后的模型）在大规模时能降低成本——例如 BuzzFeed 分享过他们微调开源 LLM 把成本降低了 **80%**。

**【扩展】**

**① 自托管和微调是两个独立决策**，书里放在相邻位置容易让人混淆：

| | 用 API | 自托管 |
|---|---|---|
| **不微调** | 最常见：直接调用通用模型 | 数据不出域、规避限流与弃用；用开源权重 |
| **微调** | 供应商侧微调（上传数据，或用其训练服务） | 完全自主：开源基座 + 自己的数据 + 自己的基础设施 |

“要求数据不出域”只意味着要自托管，不意味着必须微调；“需要特定格式”只意味着可能要微调，不意味着必须自托管。

**② 自托管的隐性成本**：GPU 采购或租用、推理工程师、容量规划、版本升级——这些都是固定成本，只有调用量足够大、利用率足够高时才摊薄（见第 2 章 2.4）。“自托管降低成本”的前提是规模。

**③ 开源权重是对“弃用风险”的对冲**：第 2 章讲过供应商会退役模型；如果关键业务依赖的模型被退役，手里有一份可自托管的权重，就把“紧急迁移”变成了“路由切换”。所以即使平时用 API，**保留一条经验证过的开源备选路线**，是合理的战略保险。

**④ 2024–2026 年的一个趋势**：高质量开源权重模型的出现，让“自托管 + 不微调”成为数据敏感行业可行的方案，这在两年前还不现实。这加强了书中的“别怕自托管”，但没有削弱“先从 API 起步”。

## 迭代到卓越（Iterate to Something Great）

**【原文】** 要长期保持竞争优势，需要思考模型之外的东西——什么会让你的产品与众不同。执行速度固然重要，但不该是你唯一的优势。

### 模型不是产品，模型周围的系统才是

**【原文】** 对不造模型的团队来说，模型的快速创新是利好：他们从一个 SOTA 迁移到下一个 SOTA，追逐上下文长度、推理能力、性价比的提升，做出越来越好的产品。这种进步令人兴奋，也**完全可以预期**。合在一起看，这意味着**模型很可能是系统里最不持久的组件**。

相反，把精力放在能提供持久价值的东西上：

| 组件 | 作用 |
|---|---|
| **评测底盘**（evaluation chassis） | 可靠地衡量你的任务在不同模型上的表现 |
| **护栏**（guardrails） | 不论用什么模型，都防止不理想的输出 |
| **缓存**（caching） | 通过完全绕开模型来降低延迟与成本 |
| **数据飞轮**（data flywheel） | 驱动上述一切的迭代改进 |

这些组件比原始模型能力形成**更厚的产品质量护城河**。

但应用层也不是没有风险：**不要把剪刀对准 OpenAI 等模型提供商为了提供可用的企业软件而必须剪的同一头牦牛。** 例如，有些团队投入构建工具来校验专有模型的结构化输出；在这里做最小投入是重要的，但深度投入不是好的时间用法——OpenAI 必须保证你请求函数调用时得到合法的函数调用，因为所有客户都要这个。在这里使用“**战略性拖延**”：构建你绝对需要的，等待供应商能力的自然扩展。

**【扩展】**

**① 为什么“模型是最不持久的组件”？** 因为它的迭代速度最快、可替代性最高、而且不由你控制。一个组件越容易被替换，越不能作为护城河。**护城河来自难以被替换的东西：难以复制的数据、难以迁移的集成、难以赢得的信任。**

**② 哪些是“供应商的牦牛”？（我的清单，随时更新）**

| 很可能会被供应商做掉 | 为什么 | 你该做什么 |
|---|---|---|
| 结构化输出/函数调用校验 | 所有客户都需要 | 用原生能力，不深度自研 |
| 内置 RAG / 文件搜索 / 网页搜索 | 平台功能 | 用它做原型与通用场景 |
| 对话记忆、长期记忆 | 平台功能 | 只在领域专属记忆上自建 |
| 提示缓存 / 前缀缓存 | 基础设施 | 利用，不自建 |
| 通用内容审核、PII 检测 | 通用能力 | 用现成的，再加领域规则 |
| 通用聊天界面、语音转写 | 商品化 | 不做差异化 |

**③ 用 Wardley 地图理解“战略性拖延”**：Simon Wardley 的地图把组件按演化分为“创世 → 定制 → 产品 → 商品”。一个组件越靠右（越商品化），越不值得自己投入。所谓“战略性拖延”，就是**识别那些正在快速右移的组件**——现在自己做很贵，一年后就是平台自带功能。结构化输出正是这样：2024 年还要靠 Instructor、Outlines 这类库来保证，一年后成了 API 原生能力。

**④ 两年多后的验证与修正**：作者的判断基本正确——结构化输出、内置 RAG、记忆、连接器都成了平台能力。但有两处需要补充：
- **“缓存”作为护城河变薄了**：前缀缓存已成为供应商的基础设施。仍属于应用层的“精确匹配响应缓存”有价值，但很难称护城河。
- **作者的清单少了“分发”与“工作流集成”**。两年后的市场给出了答案：被认为“只是套壳”的产品，如果拥有分发渠道（用户习惯）、深度工作流集成、或领域专有数据，就能活下来并壮大；而只有 Prompt 和界面的套壳确实被淘汰了。**模型周围最持久的系统，是“用户每天在其中工作的地方”。**（这个判断的依据主要是投资机构的观点，还不是研究证据。）

**⑤ 平台风险仍在向上移动**：模型供应商不只做基础设施，也在往应用层走（记忆、连接器、Agent 功能）。“哪些是牦牛”的边界每年都在变，所以要**定期重新画这张地图**，而不是画一次就完事。

### 从小做起，建立信任

**【原文】** 想对所有人做所有事的产品注定平庸。要做出有吸引力的产品，公司需要专注构建**令人难忘、有粘性的体验**，让用户不断回来。

设想一个“能回答用户任何问题”的通用 RAG 系统：缺乏专精意味着它无法优先处理最新信息、无法解析领域专属格式、无法理解特定任务的细微之处。结果是用户得到浅薄、不可靠的体验，不满足需求。

解决办法是**聚焦特定领域与用例，缩小范围——深而不广**。这会做出与用户共鸣的领域专属工具。专精还让你能**坦率说明系统的能力与局限**。对“系统能做什么、不能做什么”保持透明，展示了自我认知，帮用户理解它在哪里最能创造价值，从而建立对输出的信任与信心。

**【扩展】**

**① “深而不广”与第 2 章“围绕待完成的任务”是同一件事的两个层面**：第 2 章说的是“为谁解决什么任务”，本章说的是“产品范围的取舍”。二者都指向“专精”。

**② 专精带来的是可度量的改进**：范围窄 → 评测集更聚焦 → 失败模式更具体 → 改进可被评测捕捉 → 用户感知到进步。通用产品做不到这一点，因为“什么算好”本身就不清楚。

**③ “透明”的落地方式（我的例子）**：在产品里明确写“我能做什么/我不做什么”；在回答里显示引用来源；检索不到时明确说“资料里没有”；对低置信度的问题提示“请核对”。这些都是把第 1 章的“允许说不知道”变成产品语言。

**④ 专精不等于永远小**：先在一个窄场景做到令人难忘，再向相邻场景扩展——这是常见的路径。关键是先有一个“用户离不开”的点。

### 建 LLMOps，但理由要对：更快的迭代

**【原文】** DevOps 从根本上讲不是可复现的工作流、不是“左移”、也不是赋能“两个披萨团队”——它更不是写 YAML 文件。

**DevOps 是缩短工作与结果之间的反馈循环，让改进累积而不是让错误累积。** 它的根可以经由精益创业运动追溯到精益制造和丰田生产方式（TPS），以及其对**快速换模**（SMED）和**改善**（Kaizen）的强调。

MLOps 把 DevOps 的**形式**搬到了 ML：可复现的实验、一体化套件——当然，还有海量的 YAML。但作为一个行业，**MLOps 没有继承 DevOps 的功能**：它没有缩短模型与它在生产中的推理和交互之间的反馈鸿沟。

令人欣慰的是，LLMOps 已经不再纠结于“Prompt 管理”这类“小心眼里的怪物”（作者戏仿爱默生的名句），而转向真正阻碍迭代的问题：**生产监控与持续改进，由评测把它们连接起来。**

已经有面向聊天与编程模型的中立、众包评测的交互式竞技场——一个集体迭代改进的“外循环”。LangSmith、Log10、LangFuse、W&B Weave、HoneyHive 等工具承诺不仅收集生产中系统结果的数据，还通过深度集成开发来改进系统。**拥抱这些工具，或自己造。**

**【扩展】**

**① 把 DevOps 的四个关键指标翻译成 LLM 版**（参考《Accelerate》一书对 DevOps 的度量）：

| DevOps 指标 | LLM 应用里的对应 | 怎么测 |
|---|---|---|
| **前置时间** | 从“一个改动的想法”到“得出它是否有效”的时间 | 小时/天级为健康 |
| **部署频率** | Prompt/模型/检索变更上线的频率 | 周级比季度级好 |
| **变更失败率** | 变更导致评测回归的比例 | 有评测才知道 |
| **恢复时间** | 发现线上质量问题到回滚的时间 | 依赖监控与影子流水线 |

**没有评测与监控，这四项都测不了**——这正是作者说“MLOps 没继承 DevOps 功能”的含义。

**② 内循环与外循环**：
- **内循环**（开发时）：改 Prompt → 跑评测 → 看结果，分钟级；
- **外循环**（生产中）：线上样本 → 发现失败模式 → 补进评测集 → 触发内循环。

LLMOps 工具的价值不在于“管理 Prompt”，而在于**把外循环接通**。两年后，追踪与可观测性工具已经商品化；**仍然需要自己做的，是把生产数据和评测连起来的那一段**。

**③ SMED 与 Kaizen 的启示**：SMED 说的是“换模时间决定小批量生产是否可行”——对应到 LLM，评测跑得越快，小步实验越可行。Kaizen 说的是持续的小改进——对应到 LLM，每天看数据、每天补一条断言（第 2 章 1.2）。丰田的这两条原则，恰好是本章“更快的迭代”的两个支点。

**④ 一个完整迭代回路的设计（我的示例）**

```
线上日志 → 每日抽样 + 错误分桶 → 新失败模式
   → 固化为评测用例（内循环保护）
   → 修改 Prompt / 检索 / 模型 → 离线评测 → 影子流量 → 灰度 → 回到线上
```

每一环都要有工具支撑，但**每一环的“规则”是你自己的**——这呼应了第 2 章“流程先于工具”。

### 不要自建你能买到的 LLM 功能

**【原文】** 多数成功的企业不是 LLM 企业；同时，多数企业都有被 LLM 改进的机会。

这对观察常常误导领导者，让他们仓促地给系统加装 LLM，成本更高、质量更低，还作为“冒牌的”、装点门面的“AI”功能发布——配上如今人人害怕的闪光图标。更好的做法是：**专注于真正契合产品目标、增强核心运营的 LLM 应用。**

考虑几个浪费团队时间的“误入歧途”：
- 为你的业务自建 Text-to-SQL；
- 建一个和你的文档聊天的机器人；
- 把公司知识库接入客服机器人。

这些是 LLM 应用的 “hello world”，但**几乎没有任何产品公司应该自己建**。它们是很多企业的共性问题，“有前景的 Demo”与“可靠的组件”之间差距很大——这正是软件公司的传统领地。把宝贵的研发资源投入到“当届 Y Combinator 批次正在集体攻克”的通用问题上，是浪费。

如果这听起来像老生常谈的商业建议，那是因为在当前炒作浪潮的兴奋中，很容易把任何“LLM”的东西误当成尖端的、增值的差异化，而没注意到**哪些应用早已是老生常谈**。

**【扩展】**

**① 两年多后的验证：预测几乎完全正确**。书中列的三件事，今天都已是可以直接买到/内置的功能：
- Text-to-SQL：通用模型 + 数据库连接器即可完成，多数平台提供；
- “和文档聊天”：笔记、办公套件、知识库工具的标配；
- 知识库 + 客服机器人：客服平台的内置功能。

“越通用、越早被商品化”——这正是 2.1 说的“牦牛”。

**② 但要避免反向误解**：作者不是说“这些功能没用”，而是说“**不要把它们当作自研的重点**”。你仍然需要这些能力，只是应该买——然后把精力放在把它们**嵌进你的领域工作流**。

**③ “买能力、建流程”的判断标准（我的总结）**

| 问题 | 若“是” → 倾向买 | 若“是” → 倾向建 |
|---|---|---|
| 别家公司也需要这个功能吗？ | 是（通用） | 只有你的领域需要 |
| 模型供应商可能明年就内置吗？ | 是 | 不会（涉及你的数据与流程） |
| 做好它需要领域知识吗？ | 不需要 | 需要 |
| 它是你的差异化来源吗？ | 不是 | 是 |

**④ 一个真实的灰色地带**：Text-to-SQL 在**你自己的、复杂的业务 Schema** 上，仍然是一个需要打磨的工程问题——但打磨的对象是“你的数据模型与业务规则”，而不是“Text-to-SQL 这个能力”。买前者，建后者。

## AI 在环；人在中心

**【原文】** 当下，LLM 应用是脆弱的。它们需要大量的安全防护与防御性工程，行为仍然难以预测。但**在范围严格限定时，它们可以极其有用**。这意味着 LLM 是**加速用户工作流的优秀工具**。

虽然想象 LLM 应用完全替代一个工作流或一个岗位很诱人，但**今天最有效的范式是“人机半人马”**（cf. 半人马国际象棋）：当有能力的人与为他们快速使用而调优的 LLM 能力配对时，生产力和做事的幸福感都能大幅提升。LLM 的旗舰应用之一 GitHub Copilot 展示了这类工作流的力量——GitHub 方面表示，开发者反馈说使用 Copilot 与 Copilot Chat 时更有信心，因为写代码变得更容易、更少出错、更可读、更可复用、更简洁、更易维护、更有韧性。

对于长期做 ML 的人，可能会立刻想到“人在回路”（HITL），但先别急：**HITL 机器学习的范式是让人类专家确保模型按预期运行**；这里相关但更微妙——**今天，LLM 系统不应该是多数工作流的主要驱动者，它们只应是一种资源。**

以人为中心，问“LLM 如何支持他们的工作流”，会带来显著不同的产品与设计决策。最终，这会让你做出**与那些试图把全部责任迅速“外包”给 LLM 的竞争对手不同的产品**——更好、更有用、风险更低的产品。

**【扩展】**

**① “半人马”从哪来？** 1997 年深蓝战胜卡斯帕罗夫之后，卡斯帕罗夫在 1998 年提出“高级国际象棋”：人和电脑组队下棋，他一直主张这种增强模式。2005 年起的“自由式国际象棋”比赛里，**人机组合能战胜单独的机器**，强手配一台普通电脑也能战胜国际象棋超级计算机。

**② 这个思想比 LLM 老得多**：J. C. R. Licklider 在 1960 年的《人机共生》中就提出，人与机器应协作完成各自擅长的事。

**③ 实证证据（2023 年）**：
- 客服场景：生成式 AI 助手使生产力提升约 14%，**对新手帮助最大**（[Brynjolfsson, Li & Raymond, 2023](https://arxiv.org/abs/2304.11771)）；
- 写作任务：质量提升、时间下降（Noy & Zhang, *Science*, 2023）；
- **“参差不齐的技术前沿”**：对前沿之内的任务，AI 让人表现更好；对前沿之外的任务，使用 AI 反而让人变差（Dell'Acqua et al., 2023，哈佛商学院工作论文 24-013）——这篇论文里就用了“cyborg”与“centaur”来描述两类人机协作方式。

**④ “AI 只应是资源，不应是主要驱动者”——这条在两年后需要修正**：
- 对**可验证、低风险、高频**的任务（写代码跑测试、搜索调研、批量格式转换），Agent 已经可以当“驾驶者”，人退到“审查者”；
- 对**不可验证、高风险、低频**的任务（医疗、法律、对外沟通），人仍是驾驶者，AI 是副驾。

作者的**精神**（人对结果负责）仍然成立；但**回路的形状变了**：人从“每一步操作的人”变成“审查结果的人”。产品设计的难点随之变成了：**如何让人高效地审查一个自主系统的工作**（这本身就是新的 UX 问题）。

**⑤ 人机协作的三个风险（书中没有强调）**：
- **自动化偏见**：人倾向于接受机器的建议，审查变成橡皮图章；
- **技能退化**：长期依赖会让人的判断力下降，一旦 AI 出错，人已无力察觉；
- **虚假的信心**：流畅的输出让人误以为正确。

对策：可验证的输出（引用、可运行的代码）、随机插入“已知错误”来校准审查者的注意力、保留人工“最终签字”的仪式。

## 从 Prompt、评测与数据收集开始

**【原文】** 前面各节给了一大堆技术与建议。来看最小有用的集合：如果团队想做 LLM 产品，从哪里开始？

过去一年里，作者看到了足够多的例子，开始有信心：成功的 LLM 应用遵循一条一致的轨迹。核心思想是**从简单开始，只在需要时增加复杂度**。一个不错的经验法则是：**每提升一个复杂度层级，通常需要比上一级至少多一个数量级的努力**。

### Prompt 工程优先

**【原文】** 先做 Prompt 工程。用第 1 章讲的所有技巧——思维链、n-shot、结构化输入输出，几乎总是好主意。**先用能力最强的模型做原型**，再去尝试从较弱的模型里挤出性能。

**只有当 Prompt 工程达不到期望表现时，才考虑微调。** 如果有非功能需求（数据隐私、完全控制、成本）阻碍了专有模型的使用、因而需要自托管，微调会更常出现。但**要确保同样的隐私要求不会阻碍你用用户数据做微调**。

### 建评测，启动数据飞轮

**【原文】** 即使刚起步的团队也需要评测。否则你不知道 Prompt 工程是否足够，或者微调模型何时可以替换基座。

有效的评测是任务专属的、反映预期用法的。作者推荐的第一级评测是**单元测试**：这些简单的断言检测已知或假设的失败模式，帮助推动早期设计决策。也参见分类、摘要等任务专属的评测。

单元测试和基于模型的评测有用，但**不能替代人工评估**。让人使用你的模型/产品并反馈。这有双重目的：衡量真实世界的表现与缺陷率，同时收集高质量标注数据，用于微调未来的模型。这形成正反馈循环，也就是**数据飞轮**，随时间复合：

1. 用人工评估衡量模型表现和/或发现缺陷；
2. 用标注数据微调模型或更新 Prompt；
3. 重复。

例如，在审计 LLM 生成的摘要时，可以给每个句子打上细粒度反馈：事实不一致、不相关、风格差。然后用这些“事实不一致”标注训练幻觉分类器，或用“相关性”标注训练奖励模型。另一个例子：LinkedIn 分享过用基于模型的评估器来估计幻觉、负责任 AI 违规、连贯性等。

**通过创建价值随时间复合的资产，我们把建评测从纯粹的运营支出升级为战略投资，并在此过程中建起了数据飞轮。**

**【扩展】**

**① “每级多一个数量级的努力”——把阶梯画出来**

| 层级 | 做什么 | 相对努力（示意） | 何时上这一级 |
|---|---|---|---|
| 1 | Prompt 工程 + few-shot + CoT | 1× | 总是从这里开始 |
| 2 | 加 RAG | ~10× | 需要模型不知道的知识 |
| 3 | 多步工作流 / Agent | ~100× | 单次调用解决不了，且能设计验证点 |
| 4 | 微调 | ~1000× | 行为/格式/成本确有瓶颈，数据充足 |
| 5 | 继续预训练 / 从零训练 | 更高 | 见 1.1 的四个条件 |

（倍数是示意，不同任务差异很大；但“越往上越贵一个数量级”的方向是对的。）

**② “先用最强模型做原型”的深意**：它把“任务可不可行”和“怎样做最便宜”两个问题分开回答。先用最强模型证明可行，再按第 2 章 2.4 下沉到小模型。反过来做（先纠结用什么模型），会把自己的工程问题误判成模型能力问题。

**③ 数据飞轮的四个必要条件（我的总结）**——多数“飞轮”停在第 3 条：

1. **有使用**：没有足够的用户与调用量，就没有数据；
2. **有信号**：用户行为能反映对错（第 2 章 3.2 的 UX 设计）；
3. **有学习机制**：有管线把标注变成评测、Prompt 或微调；
4. **有可度量的改进**：能证明飞轮转了一圈之后产品确实变好。

只有同时满足，飞轮才成立；否则只是“收集了数据”。

**④ 评测资产会折旧**：评测集反映的是某个时刻的数据分布与标准。用户变了、任务变了、模型变强了（旧失败模式不再出现），评测就要更新（第 2 章的“标准漂移”）。所以“把评测当战略投资”是对的，但**这是一项需要持续维护的资产**，不是一次性的投入。

**⑤ 一个起步两周的计划（我的示例）**

| 天 | 做什么 |
|---|---|
| 1–2 | 用最强模型写第一版 Prompt；跑 20 条真实输入，人工看 |
| 3–4 | 把看到的失败模式写成 5～10 条断言 |
| 5–7 | 做 UX 雏形，让 5 个真实用户试用并纠正；把纠正记录下来 |
| 8–9 | 建一个 50～100 条的评测集（真实输入 + 人工标注） |
| 10 | 决定：继续 Prompt 迭代，还是需要 RAG |
| 11–14 | 搭日志与每日看样本的习惯；排下一轮实验 |

## 低成本认知的大趋势

**【原文】** 1971 年，Xerox PARC 的研究者预测了未来——我们现在生活的联网个人电脑世界。他们通过在以太网、图形渲染、鼠标、窗口等技术上的发明帮助催生了这个未来。

但他们还做了一件事：**看那些非常有用（例如视频显示器）但还不经济（驱动显示器所需的足够 RAM 要数千美元）的应用，然后看该技术的历史价格趋势（摩尔定律），预测这些技术何时变得经济。**

**我们可以对 LLM 做同样的事**，尽管没有像“每美元晶体管数”那样干净的指标。选一个流行的长期基准（如 MMLU）和一个一致的输入方式（五样本提示），比较不同表现水平的模型运行成本随时间的变化。书中的图 3-1 显示：**固定成本下能力快速上升；固定能力水平下成本快速下降。**

书中的三组数字：
- 自 OpenAI 的 davinci 模型以 API 形式发布以来的四年里，在该任务上表现相当的模型运行一百万 token（约本书一百份）的成本，从 **20 美元降到不足 10 美分**——**减半周期仅 6 个月**。
- 2024 年 5 月，Meta 的 LLaMA 3 8B 通过 API 或自托管运行只要 **每百万 token 20 美分**，而表现与 text-davinci-003（让 ChatGPT 震惊世界的那个模型）相近；后者发布时约每百万 token 20 美元——**18 个月里两个数量级**，而摩尔定律在同一时间里只预言翻倍。（注：书中此处写作“2023 年 11 月发布”，应为 **2022 年 11 月**，否则与“18 个月”不符。）

一个“有用但还不经济”的应用：**给电子游戏角色赋予生成能力**（Park 等人“生成式 Agent”那一类），书里引的一篇论文（Lyfe Agents）估计成本为**每小时 625 美元**。自 2023 年 8 月那篇论文发表以来，成本已下降约一个数量级到**每小时 62.50 美元**；再过九个月可能降到**每小时 6.25 美元**。而 1980 年《吃豆人》发行时，今天的 1 美元能买一局，玩几分钟到几十分钟——按每小时 6 局算，约**每小时 6 美元**。这个餐巾纸算术提示，**令人信服的 LLM 增强游戏体验会在 2025 年左右变得经济。**

这些趋势还很新，只有几年。但没有理由预期它会在近几年放缓。即便算法和数据集的“低垂果实”（如超越“Chinchilla 比率”——每参数约 20 个 token）被摘完，数据中心与硅片层面更深的创新与投资会接上。

**这也许是最重要的战略事实：今天完全不可行的演示或研究论文，几年后会成为高级功能，再过不久成为商品。我们应当据此构建系统和组织。**

**【扩展】**

**① 这个方法可以自己复现——“能力调整后的价格”**：
1. 选一个与你业务相关的基准，设定一个“够用”的分数阈值；
2. 找出每个时间点上**达到该阈值的最低价模型**；
3. 画出价格随时间的曲线；
4. 用曲线预测你关心的功能何时变得经济。

注意两点：基准会饱和、会被训练数据污染，所以要定期换基准或用私有评测；阈值要对应真实的业务质量，而不是榜单分数。

**② 两年多后的验证（结论：方向正确，但有一个重要的新现象）**：
- **固定能力的价格**：业界跟踪显示，同等能力的推理价格在 2021–2025 年间大约每年下降 10 倍（a16z 在 2024 年底的“LLMflation”分析也给出了同样的量级），**与作者的“减半期 6 个月”相比甚至更快**。
- **前沿旗舰的价格并没有下降**：顶级模型的输出价格一直维持在每百万 token 几十美元的量级，没有明显下行趋势。
- **每张账单没有下降 10 倍**：因为推理模型引入了“思考 token”，Agent 的单次任务消耗的 token 比单次调用多几个数量级。结果是“**商品化认知**”与“**前沿认知**”的价格出现分叉：便宜的更便宜，昂贵的用得更多。

**这对战略的含义**：作者的“按明天的成本规划”仍然成立，但要区分两类功能——

| 功能类型 | 成本走势 | 规划建议 |
|---|---|---|
| 分类、抽取、摘要、有界问答 | 快速趋近免费 | 今天就可以设计“以前因成本不敢做”的高频功能 |
| 多步 Agent、深度推理、长上下文综合 | 单价降，但单任务用量涨 | 以“每任务成本”而非“每 token 成本”做预算，并设计缓存、路由、提前终止 |

**③ 杰文斯悖论**：价格下降 → 用量暴涨 → 总支出可能上升。2026 年中国算力大会上有公开数据称，日均 token 调用量两年增长超过千倍，高端模型价格甚至在供需紧张时上涨（据新闻转述，量级供参考）。所以“低成本认知”的另一面是“高总量认知”。

**④ 我自己的餐巾纸算术**：设想“每周为 10 万用户各生成一份个性化深度报告”，每份输出 5000 token，每周就是 5 亿输出 token。按前沿模型输出每百万 token 10 美元计，约 5000 美元/周；按商品化模型每百万 0.5 美元计，约 250 美元/周。（价格为示意。）同样的功能，两年前是“不可行”，今天是“高级功能”，两年后是“标配”——正是作者说的三段论。

**⑤ “能力过剩”（capability overhang）**：这个说法 2022 到 2023 年经 Jack Clark 的 Import AI 通讯流行开来，说的是模型的能力往往超过使用它的产品——产品没有用上模型已有的能力。这与成本下降是一体两面：**你的竞争对手明天就能用今天“不经济”的能力做出你没想到的功能。**

## 受够了 0→1 的 Demo，是时候做 1→N 的产品

**【原文】** 做 LLM Demo 非常有趣：几行代码、一个向量数据库、一个精心写的 Prompt，就能创造魔法。过去一年，这种魔法被比作互联网、智能手机、甚至印刷术。

但不幸的是，正如任何做过真实软件的人所知，**在受控环境中能跑的 Demo 与能在规模上可靠运行的产品之间，有着天壤之别。**

以自动驾驶汽车为例：第一辆由神经网络驾驶的汽车出现在 1988 年。25 年后，Andrej Karpathy 才第一次坐上 Waymo 的 Demo。又过了十年，公司才拿到无人驾驶许可。**从原型到商业产品，是 35 年的严谨工程、测试、打磨与监管沟通。**

作者在过去一年——LLM 应用的“第 1 年（of N 年）”——细致观察了业界与学界的起落。他们希望这些经验——从严谨的运营技术，到“该在内部建哪些能力”的战略视角——能在第 2 年及以后帮到大家。

**【扩展】**

**① 自动驾驶的“35 年”之后**：2024–2026 年，Robotaxi 从少数城市的试验扩展到更大范围的商业化运营。这再次印证了同一规律：**Demo 到产品很慢，但一旦跨过可靠性的门槛，扩张可以很快。** 对 LLM 产品的启示是：耐心打磨可靠性的阶段无法跳过，但它是后续扩张的前提。

**② 为什么 Demo 和产品之间差这么多？** 可以用前两章的内容回答：
- Demo 没有评测（第 1 章 4.x），所以不知道自己在多少比例的输入上是对的；
- Demo 没有处理边界情况与失败模式（第 2 章数据）；
- Demo 没有 UX 来收集反馈与纠正（第 2 章 3.2）；
- Demo 没有迁移与回滚机制（第 2 章 2.3）；
- Demo 没有风险分级（第 2 章 3.4）。

每一项都是“一个数量级”的努力（4.2 的阶梯）。

**③ LLM 应用会更快吗？** 我认为：对低风险、可验证、纯软件的场景，会快得多——没有物理世界的监管与安全问题；对高风险场景（医疗、法律、金融决策），35 年的时间尺度并不夸张，因为它取决于监管与信任，而不取决于模型能力。

## 书里说得不够或可以商榷的

第 3 章是全书“预测”最多的一章。哪些预测被验证、哪些要修正，已经写在上面各节的【扩展】里，逐条的现状核对放在[第四篇](/posts/llm-year-04/)。这里只记本章书里说得不够，或者我觉得可以商榷的地方：

1. **分发被低估**。整章把“系统”定义为技术组件，但两年后活下来的“套壳”公司，多数靠的是分发与工作流——这不是技术问题，而是产品与渠道问题。
2. **数据飞轮讲得太顺**。飞轮需要“使用 → 信号 → 学习机制 → 可度量改进”四环同时成立；多数产品有数据但没有学习机制，飞轮不转。
3. **平台风险只讲了“供应商会做掉功能”，没讲“供应商会向上做工作流”**。后者对应用公司的威胁更大。
4. **监管与合规几乎缺席**。对高风险行业，“低成本认知”能否变成产品，取决于合规而非价格。
5. **“人在中心”与“1→N”两节之间的张力**：要做到 1→N，很多环节必然自动化；人的角色应从“操作者”变为“审查者与负责者”。书中没有明说这个转变。
6. **原书的一个笔误**：text-davinci-003 的发布年份应为 2022 年而非 2023 年。
7. **生成式游戏 NPC 的成本预测方向对，但没见到它成为主流玩法的公开证据**。成本只是必要条件，产品体验与延迟同样重要。

## 贯穿全章的底层思想（提炼）

读完第 3 章，我把散落的建议归纳为**七条原则**：

1. **先验证，再投入。** PMF 之前不买 GPU；Prompt 没到瓶颈不微调；先用最强的模型证明可行，再谈降本。
2. **模型是租来的能力，系统才是自己的资产。** 评测、护栏、飞轮、工作流、分发——越难被替换的，越值得建。
3. **不替供应商刮牦牛。** 识别正在快速商品化的组件，做最小投入，等平台补上；定期重画这张地图。
4. **小切口、深下去、把边界说清楚。** 专精带来可度量的改进，透明带来信任。
5. **迭代速度就是竞争力。** LLMOps 的唯一正当理由是缩短反馈循环——内循环靠评测，外循环靠生产数据。
6. **人是判断的中心。** 半人马优于纯机器；但回路的形状在变——从“人操作”到“人审查”，责任不变。
7. **按明天的成本做今天的规划。** 今天的不可行是明年的高级功能、后年的商品；但要区分“商品化认知”与“前沿认知”。

与前两章的连接：第 1 章“用确定性包裹概率性”，第 2 章“用流程与产品包裹不确定性”，第 3 章“用取舍与时间维度包裹不确定性”——**在快速变化的技术上，唯一可靠的战略是知道什么会变（模型）、什么不变（数据、工作流、信任、迭代能力），并把资源押在不变的东西上。**

## 落地检查清单

**投入与选型**
- [ ] 是否已用 API + 最强模型验证了可行性，而不是先纠结选型？
- [ ] 若考虑微调：是否有评测证明 Prompt/RAG 不够？数据是否不公开且充足？是否能随基座更新重做？
- [ ] 若考虑自托管：理由是否是数据不出域、规避限流/弃用或规模化成本？是否算过利用率与固定成本？
- [ ] 是否保留了一条经验证的开源备选路线，以对冲模型弃用？

**护城河**
- [ ] 是否列出了自己的“牦牛清单”——供应商明年会内置的能力？是否每年重画一次？
- [ ] 评测底盘、护栏、飞轮是否在持续积累？是否还缺分发与工作流集成？
- [ ] 是否有“使用 → 信号 → 学习机制 → 可度量改进”的完整飞轮？停在哪一环？
- [ ] 产品范围是否“深而不广”？是否向用户透明说明了能力边界？

**迭代与人机协作**
- [ ] 是否测量了前置时间、部署频率、变更失败率、恢复时间？
- [ ] 外循环是否打通：线上样本 → 评测集 → 内循环？
- [ ] 是否按“可验证性 × 风险 × 频率”决定了人是驾驶者还是审查者？
- [ ] 是否有防止“橡皮图章”审查的机制？

**面向未来**
- [ ] 是否画过“能力调整后的价格”曲线？是否据此排期了“今天不经济”的功能？
- [ ] 是否按“每任务成本”而非“每 token 成本”做预算？
- [ ] Demo 与产品之间的差距（评测、边界、UX、迁移、风险分级）是否逐项有人负责？
